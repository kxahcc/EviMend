# 最小实验与启动计划

> 2026-09-15：正式数据已到位，原公开基准与样本数安排保留为历史规划。本批数据的环境要求、案例划分及首轮 18 次候选方案见 [最新评估](data-b-assessment-2026-09-15.md)。

状态：计划，尚未执行模型评测。目标是用有限成本决定下一步投入；不是用少量案例预先证明论文结论。

## 1. 公开数据的使用顺序

| 数据 | 适合验证什么 | 当前核验与限制 | 选择 |
|---|---|---|---|
| [BugsInPy](https://github.com/soarsmu/BugsInPy) | 真实 Python 缺陷的复现、日志生成、修复与回归 | 已核验 3 个案例的版本与测试入口；旧依赖需独立环境 | 第一批环境验收候选 |
| [Defects4J](https://github.com/rjust/defects4j) | Java 定位/修复及动态诊断近邻比较 | 当前主线要求 Java 11，历史版本要求不同；比赛语言未知 | Java 路线或论文扩展 |
| [SWE-bench](https://github.com/SWE-bench/SWE-bench) | 仓库级任务及成熟 harness 集成 | 原生输入为 issue，不能直接冒充运维日志任务 | 底座参照或明确标注的日志适配实验 |
| [CI-Repair-Bench](https://github.com/RabeyaMuna/CI-REPAIR-BENCH) | 真实 CI 日志到仓库修复 | README 要求账号及 benchmark 组织访问；CI 成功不等于所有语义正确 | 条件满足后再考虑 |

三个已核验案例是 black-1、tornado-1、httpie-1，元数据见 [候选文件](../../resources/preparation/public-case-candidates.json)。它们只证明公共材料可定位，不证明可复现；不按预期模型成败选择这些案例。拓展样本前先做环境验收。

公开缺陷生成的测试失败日志应标记为“从测试执行生成”，不得称为真实生产日志。若正式私仓输入不同，首先修改数据适配与实验条件，不假定公开榜单可直接迁移。

## 2. 任务输入与评判的隔离

准备两个明确设置，不混合汇总：

- 可复现设置：提供 buggy 源码、故障日志、允许执行的复现入口和已有测试。研究证据验证和补丁效果。
- 静态设置：只提供源码与日志。模型不能调用不存在的复现能力；重点评价定位、建议与可完成的修复。

参考补丁、fixed 版本、根因标注、隐藏评测测试留在独立 evaluator 中，不能装入求解容器或通过 Git 历史访问。当前候选 JSON 是开发准备元数据，含 evaluator 字段，未来不能整体作为 Agent 输入；目录命名本身不构成隔离。

允许用开发用例的正确位置做额外诊断实验，但它不计入任何正式对照成绩。给位置后改善只支持定位瓶颈的推断，不是理论上界。

若使用 SWE-bench evaluator，每个不同补丁/配置/重复运行分配唯一 `run_id`。其[当前官方 README](https://github.com/SWE-bench/SWE-bench#-usage) 说明结果缓存只使用 `run_id` 和 `instance_id`，相同标识可能复用旧补丁结果。自己的记录同时保存源码、补丁、配置和测试版本的哈希；有意复用时核对这些字段。

## 3. 三个主要实验组

| 组 | 配置 | 回答的问题 |
|---|---|---|
| B0 | 同一强模型 + 冻结的基础修复 harness | 最小可靠系统能做到什么 |
| B1 | B0 + 参考已有方法的结构化诊断交接 | 成熟诊断增强能否在当前场景奏效 |
| P | B1 + 我们的证据检查、一次有界探针及采纳策略 | 新增设计相对已有增强是否有独立收益 |

所有组拿到相同原始信息、工具权限和总预算。B0/B1 也允许主动运行同类工具；差异是流程如何组织和决定调用。预处理、诊断调用、探针与回退均计费。不得给 P 额外隐藏测试或免费先验。

首轮 B1 是适配基线，不是“已经复现的 SHERLOC”。若采用原方法代码和配置，应另建明确标记的复现组。论文阶段补上近邻原方法，不能只战胜自己的简单实现。

## 4. 执行顺序

### E0：环境验收，模型运行数 0

先处理 3 个真实候选，稳定后再补到约 6 个，跨至少 3 个项目。每个案例重复运行 buggy 版本应出现目标失败；fixed 版本应通过相同目标测试。保留失败签名、环境版本、安装时间和依赖问题。

环境配置单案例建议限制 60 分钟；达限记为环境阻塞并换预先登记的候选，不能把阻塞抹掉。该规则用于准备阶段，正式评测的排除/失败处理必须在运行前冻结。

### E1：小规模方向筛选，72 次任务运行

从已验收池中构建 24 个开发案例，目标跨至少 4 个项目。按项目和自然故障现象分层，固定随机种子；不要只保留擅长的故障。

三组 × 24 案例 × 1 模型 × 1 次重复 = 72 次完整求解。逐例分析失败属于环境、定位、诊断误导、修改、验证、预算中的哪一类。

另为最多 12 个已观察到的开发失败提供正确位置参照，共最多 12 次额外运行。这个子集有意选择失败，用于诊断瓶颈；不能将其收益比例外推到全数据。

### E2：独立确认，最多 540 次任务运行

只有 E1 给出正向信号才进行。选择另 60 个案例，按项目或故障家族与 E1 隔离；三组 × 60 × 1 模型 × 3 次重复 = 540 次。使用新目录和新运行，不用按测试结果拼接的“理想回退”。

60 案例不保证有能力证明 5 个百分点提升。若区间仍跨越零，结论是证据不足；在时间允许时按估算增加独立案例，否则保留更稳的比赛版本。

### E3：机制诊断，最多 180 次额外运行

从开发池选择 30 个案例，分别把 P 的采纳策略替换为“无条件采用”和“始终执行一次探针”，保持其余部分相同；2 替代组 × 30 × 2 次重复 = 120 次。另为同案例、同版本的完整 P 配置预算 60 次参照运行，合计 180 次。

这些是诊断性消融，不冒充论文全部实验。预算默认重新运行 P；若已有完全匹配的案例、版本和重复配置，可复用并在记录中扣除，不能混用不一致的历史结果。

### 论文扩展

在独立数据上锁定完整方法、加入近邻原方法、增加第二模型和跨项目分析。样本量由观察到的成对差异与研究主指标决定；不预先承诺“60 个案例足够发论文”。私仓结果按授权决定是否公开；公开可复现部分独立成立。

## 5. 建议的时间与预算约束

正式启动后的 5–7 个工作日仅是第一轮建议：环境和基线约 2 天；诊断增强与最小改进约 2 天；筛选和归因约 1–3 天。机器运行时间另按并发与环境测量，不能把开发人日当求解耗时。

E1 及瓶颈参照合计最多 84 次模型求解。E2/E3 按阶段开放，不一次性提交大批任务。配置见 [experiment-plan.json](../../resources/preparation/experiment-plan.json)。费用情景是算术假设，不是模型价格或实测消耗。

增加模型、语言和 Skills 前先检查是否对应已观察到的失败。第一轮不训练大模型，不建立全语言代码图，不做多 Agent 辩论集群，不为了模型数量增加实验矩阵。

## 6. 比赛数据到位时的验收项

确认源码语言与规模、日志/Trace 配对、复现入口、环境权限、网络与外部模型限制、资源预算、根因标注粒度、测试可见性、是否允许跨案例记忆、数据发表权限及截止日期。这些来自未决条件，当前没有假定答案。

选取代表案例做输入适配，随后重跑冻结基线。针对正式数据的调整只在允许的开发部分完成；最终评测部分保持独立。
