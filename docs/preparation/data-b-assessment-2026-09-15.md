# data_B 到位后的数据核查与路线调整

日期：2026-09-15。范围：本地只读盘点、README/指南/构造文档阅读、日志解析、代表源码与测试审查。未编译应用、未连接设备、未运行模型修复或 Hypium。

## 1. 现在可以明确的项目定位

本批数据是 **HarmonyOS 应用、ArkTS 为主、通过业务操作触发的注入式运行时故障修复**。已有源码、jscrash 和部分自动化操作脚本。它与之前用 Python/Java 公开缺陷准备的通用修复设想有明显差别。

建议保留“强模型 + 可靠执行底座 + 可单独验证的增量机制”，把技术重点收敛为：

> 从崩溃栈出发，追踪被破坏的运行时约束及其上游来源，生成保留业务语义的修复，再按验证能力选择局部检查或设备回放。

当前最值得投入的是 ArkTS 数据适配、可靠评测和针对故障类型的诊断/验证策略。微调暂不作为启动依赖；Skills 的作用可以提前，但内容应是可验证的通用约束与动作，不是具体案例答案。

## 4. 从源码看到的困难，比“找报错行”更具体

以下是静态审查支持的诊断示例，不是已验证补丁或模型成绩。

| 案例 | 日志指向与当前源码 | 实际应验证的约束 |
|---|---|---|
| BookRead2 / 004 | `BookViewListPage.ets:21` 调用 `books!.load`，初始化在下一行 | 生命周期中的初始化先于使用，修复后仍能正常显示书目 |
| ComprehensiveTool1 / 001 | `ResourceManageVM.ets:83` 读取 `list[index2].sortNum`，此前只检查部分 `index1` 条件 | 排序两端索引都应有效；不能通过取消排序来消除崩溃 |
| Exam1 / 019 | 栈顶先出现框架对象创建，业务栈反复进入 `appendLearningOrder` | 沿 nextId 的遍历应终止；需要检查循环关系及业务顺序，不能只改对象分配语句 |
| AudioEditing1 / 021 | `getFloat32` 在第 58 行越界；第 52 行循环使用 `<= totalFrames` | 读宽度、偏移、声道数、采样步长和缓冲区长度共同决定合法范围；报告里的 `getInt16` 已非当前代码 |
| HouseholdService1 / 022 | 第 22 行按字符个数分配字节，第 23 行按同样数量创建 Uint16 元素视图 | 字节数与元素数一致，且生成的校验值仍与 verify 兼容 |
| WebShortDrama1 / 024 | B2 对分享文本创建 Uint32Array；B3 对反馈缓存创建 Int32Array | 数据字节长度、视图宽度及尾部数据处理；两个变体不能互相套用文件位置 |

这些例子支持把研究重点放在“崩溃点到错误约束来源的追踪”和“保持功能的验证”。它们尚不能证明某种新方法优于强模型直接分析。

## 5. 现有测试能证明什么

**构造契约测试：** B3 的五个 Python 测试文件主要检查故障注入、脚本规范、文件内容和历史目录状态。022 的测试甚至明确要求出现 `new ArrayBuffer(payload.length)` 这一故障表达式。把它们当修复后必须通过的测试，会奖励保留错误。部分测试还依赖原作者的绝对路径、Excel 和旧基线。

**应用模板测试：** 文件很多，但抽查的 `LocalUnit.test.ets` 是 `'abc'` 包含 `'b'`、值等于自身的模板断言。不能凭测试文件数量声称有充分业务回归覆盖。

**Hypium 场景脚本：** 提供了有价值的操作路线。审查的 021 还验证目标页面到达，并对退出后的新 jscrash 做检查；但到达页面和进程存活仍不足以证明波形内容正确。应保留路径测试，补充与修复影响相关的业务断言。

建议把结果分开记录：

1. 源码与规则检查：位置/符号/类型约束及补丁结构可检查。
2. 局部逻辑验证：可抽离逻辑的边界输入和正常输入检查。若使用 Node，只证明对应 JavaScript 片段，不能证明 ArkTS 编译或 HarmonyOS 运行正确。
3. 应用构建和设备回放：编译、安装、目标操作、新日志、功能结果及回归。

只有第 3 层满足要求后，才能报告应用运行修复成功。结果结构应保存三层状态，缺失填 unknown，不能一律折成 PASS。

## 6. 对技术路线的更新

### 工程底座

复用通用 Agent 的模型调用、工具循环和轨迹记录；把执行环境适配为 HarmonyOS 项目。之前的 Docker/Python 路线不再作为本批数据的第一入口。优先完成：日志规范化、源码映射、ArkTS 模块检索、构建配置、单案例设备回放和结果记录。

清单中的标签与报告不放入求解工作目录。文档中的 `Prompt.md` 是当年要求 Agent 注入故障的提示词，应用目录里的 `AGENTS.md` 是随数据附带的上下文；本次把它们作为数据分析材料，没有执行其中的造故障或修改系统配置指令。后续求解沙箱应显式规定允许输入，避免这些材料改变修复任务。

### 自己的方法贡献

把之前“先验证诊断是否可信”进一步具体化为：

**错误类型/栈 → 运行时约束 → 相关数据来源与控制条件 → 少量候选修复 → 分层验证。**

第一版可以只覆盖 3–4 类规则，例如初始化顺序、数组/字节边界、递归终止、动态正则。规则由通用机制及允许的开发样本形成，不能将测试案例的固定行号和答案写入规则。先用确定性规则与 LLM 组合，再判断是否值得学习选择策略。

设备运行通常包含构建、安装和 UI 导航等额外步骤，因此有必要研究“何时局部检查已经足够筛掉候选、何时必须付出设备回放成本”。实际时间与收益尚未测量，不能先声称成本一定下降。

### Skills 与微调

Skills 可承载：适用错误特征、所需证据、诊断动作、候选修复限制、正常/边界验证和退出条件。通用示例是“检查 TypedArray 的字节容量与元素数量”，不应该是“见 022 就改第 22 行”。最终仍可导出竞赛要求的标准化 Skill/Spec。

当前只有二十多个候选变体，而且模板相关性很强，不适合作为从头建立训练主线的依据。先测强模型在哪些地方持续失败，再考虑模型替换、相关资料检索或小规模蒸馏。有限数据首先用于评估和失败归因。

## 7. 启动实验应改成怎样

9 月 12 日的“24 个开发案例 + 60 个新确认案例”是数据未知时的公开基准规划。本批包内没有足够独立案例直接执行该安排，原 84 次预算也不应直接当当前默认任务。

建议先做两个 HarmonyOS 应用的环境验收；从操作链较清晰的 BookRead2 和 FitnessCenter 开始是候选选择，最终由真实构建与回放决定。

环境跑通后，用上表中 BookRead2、综合工具、FitnessCenter、Exam、AudioEditing、HouseholdService 六个机制不同的候选做开发诊断，三组单次运行共 18 次完整求解：

- B0：同一强模型，日志 + 原始源码 + 相同可用工具。
- B1：B0 加结构化栈/诊断交接。
- P：B1 加约束追踪及分层检查策略。

三组输入、可用工具和总预算一致，额外检查和回退必须计入。先测效果及失败原因，再决定扩展；重复种子不能扩充独立案例数。

剩余数据按应用/模板谱系分组保留；MoneyTrack 两版与 WebShortDrama 两版不能随机拆到开发和确认两边。正式划分还要确认主办方对当前包的用途、隐藏测试和提交接口。本轮已经阅读部分构造答案，因此这是分析者接触过标签的数据；后续评测求解器使用全新上下文和清理后的输入，不能复用本对话来声称盲测。

论文贡献仍可建立在成熟方法上升级，优先用强对照和机制消融说明新增价值。若后续没有更大独立数据，需要公开可复现扩展或获授权的新案例，不能靠重复日志、同模板副本或重复运行放大样本量。去掉栈行号、添加噪声等可以做鲁棒性实验，但必须标为变换数据，原始输入上的成绩单独保留。

## 8. 当前环境及下一步依赖

本次 PATH 检查没有找到 `hdc`、`hvigorw`、`ohpm`；当前 Python 无 `hypium`、`xdevice`、`devicetest`。三个常见 SDK 环境变量未设置。检查的两个 DevEco 安装候选目录未发现安装，不能据此断言整台电脑没有 DevEco。

数据包中未发现散落的 HAP、APP、签名 p12/p7b、`local.properties` 或 hvigor wrapper；23 个 ZIP 成员清单也未出现应用安装包。本机未发现文档引用的 `D:/bm`。应用 README 存在不同 SDK/设备要求，部分项目保留登录、支付、签名和 bundle 占位配置，需要按实际回放路线处理。

下一步最有价值的产出是：固定案例清单与源码哈希、给疑似错配材料标状态、准备隔离的求解输入、确认工具链/设备、跑通两个应用的原始失败。当前阶段不直接修正所有源码，也不运行数据包中的环境修改脚本。
