## 当前建议

采用“成熟修复 Agent 底座 → 结构化诊断增强 → 用可执行证据验证诊断的增量改进”。先建立有竞争力的可运行基线，再决定增强模块是否进入比赛版本。面向后续 CCF-B 左右的研究工作，允许在已有方法上改进；以可归因的增益、实际适用条件和复现证据突出贡献。

当前判断是工程与研究可行性判断，不是对成绩、修复率或论文录用的预测。

| 层次 | 先做什么 | 作用 |
|---|---|---|
| 可交付底座 | 强模型、成熟执行框架、故障复现、补丁验证、成本记录 | 在增强模块无效时仍有完整参赛系统 |
| 有依据的增强 | 借鉴已有研究，将定位依据和修复方向组织成紧凑诊断交给修复器 | 使用成熟思路争取效果，同时构成较强对照 |
| 自己的增量设计 | 对诊断中的关键事实进行可执行检查；必要时用少量探针验证，再决定采用或舍弃诊断 | 减少错误诊断传播；量化新增成功、引入失败与预算消耗 |
| 后续增强 | 可靠经验提炼成 Skills；必要时学习动作选择或蒸馏 | 由失败分析和剩余时间触发 |

## 为什么这条路线风险相对可控

各阶段复用执行环境、数据适配、补丁验证和轨迹记录。增强模块可以关闭，避免把比赛成败绑定到一个尚未验证的算法。单次任务内关闭诊断也要消耗此前已用预算，并不保证恢复成“从头运行基线”的效果；是否减少风险必须用完整运行验证。

建议以 [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent) 作为第一候选工程底座。已阅读其 Agent 主循环、Docker 环境接口、依赖声明与许可证，确认具有模型/环境分离、执行轨迹及调用成本记录。当前未安装、未执行，不把 README 成绩当成本项目成绩。若后续需要复杂专用工具接口，再比较 SWE-agent。

以 SHERLOC 的结构化诊断、TraceRepair / DebugRepair 的运行证据思路作为可借鉴基础。相关研究和适用边界集中记录在 [prior-art.md](prior-art.md)。初步实现若只借鉴方法，命名为“参考方法的适配基线”，不标成原作者方法复现。

## 拟实现的最小增量机制

研究问题：在总预算不变、看不到正确补丁的条件下，对诊断进行有界的证据检查，能否改善最终修复的收益与风险？

1. 从日志和代码得到候选根因，标出其引用的原始日志、源码位置和尚待证实的前提。
2. 对可机械验证的事实做检查，例如文件/行是否存在、日志是否真实包含某值、目标路径是否实际执行。把“事实存在”与“因果解释成立”分开。
3. 当修复方向依赖一个未证实前提时，选择一个能区分候选解释的低成本检查。第一版最多增加一次诊断运行；在没有可复现环境时跳过。
4. 以“支持 / 矛盾 / 未知”更新诊断。矛盾诊断不作为既定根因交给修复器；未知不等于错误，也不被伪造为支持。
5. 在剩余预算内完成修复与独立验证。记录诊断采纳、拒绝、探针开销和最终结果。

候选实现先使用确定性约束与少量规则，不先训练概率估计器，也不把模型自报置信度当作可靠概率。只有证据表明规则成为瓶颈，再考虑学习型选择器。

创新定位是“已有诊断与修复方法在日志驱动场景下的证据检查和执行策略改进”。不能单独把结构化报告、代码图、信息增益、反思或 Skills 称作首创。方法重合是设计与比较的依据，不是淘汰路线的充分理由。

## 准备突出哪些可量化贡献

| 候选贡献 | 必须比较 | 重点指标 |
|---|---|---|
| 提高修复效果 | 同模型同预算，完整系统 vs. 冻结基线与诊断增强基线 | 独立测试通过率、经审查正确修复率、首次候选通过率 |
| 控制错误诊断传播 | 有证据检查 vs. 无检查；相同诊断和工具权限 | 新增成功数、被破坏的原成功数、净收益、采纳错误诊断的比例 |
| 改善效率 | 相同成功目标下的完整运行，包含检查和回退成本 | 总 Token、实际费用、端到端时间、超时率 |
| 对比赛数据适配 | 自然日志案例及公开迁移案例 | 分故障类别、日志完整度、跨文件传播情况的效果 |

研究主指标在独立确认集运行前锁定。若选择效率路线，应同时预设质量允许损失及置信区间判据；不能看完测试结果再选择最好看的指标。

## 分阶段推进与停止条件

建议正式启动后的首轮探索限制在约 5–7 个工作日，实际按人手调整。原始竞赛截止日期和规则未给出，本文不假定具体赛程。

| 阶段 | 要拿到的证据 | 何时停止加码 |
|---|---|---|
| 环境与输入验收 | 少量真实缺陷稳定复现；修复参考版本通过；模型入口可用 | 环境不稳时优先换样例/镜像；不继续加 Agent 模块 |
| 小规模筛选 | 24 个开发案例，三组同预算对照及失败分类 | 不能挽回真实失败、或明显破坏原成功时，暂停增强 |
| 独立确认 | 新案例、重复运行、真实执行回退分支 | 改善只出现在筛选集时，比赛采用更稳的基线 |
| 比赛冻结 | 固定方法、完整验收与提交材料 | 最后约 25%–30% 时间停止增加方法模块 |
| 论文扩展 | 公开可复现数据、近邻方法对比、机制与泛化实验 | 没有足够证据时缩小主张，不把比赛成绩等同论文结论 |

停止某个增强模块不等于项目失败：底座和测试资产继续使用。可以保留工程成果，转向效率、数据适配或经验证的局部修复策略。

## 数据到位后如何分流

- 源码和日志齐全，允许复现与插桩：优先验证上述证据检查路线。
- 只有源码与静态日志：先做日志到代码的检索和诊断，动态探针不作为必要条件。
- 输入本身缺少可运行条件：把复现/环境适配排到前面，不能让方法收益被环境故障淹没。
- 故障集中于少数重复模式：增加带适用条件和回归用例的 Skills，测迁移与误用。
- 给出正确位置后模型仍频繁修错：评估更强修复模型或针对性训练；该参照是瓶颈诊断，不是正式效果。
- 基线已经接近饱和：检验降低成本或提高困难子集鲁棒性的空间；若没有空间就停止方法扩张。
