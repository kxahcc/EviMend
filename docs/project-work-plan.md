# EviMend 研究计划

状态：研究阶段计划，尚未启动新实验。最后维护：2026-10-26。

## 目标与共同主线

项目面向独立的修复 Agent 研究，以及缺陷挖掘后可回放问题的局部修复。两者共用证据、假设、补丁和检查接口，首先研究同一个问题：**证据不完整且执行有成本时，Agent 如何选择下一步调查，并在失败后修订根因判断，减少沿错误方向反复修改？**

独立研究需要多项目、独立验证和可归因的机制比较。缺陷挖掘衔接优先采用少量有源码、可复现触发、正常行为检查的网络服务或应用问题；前序系统交出的解释是待核查材料，不自动视为真值。

当前先迁移维护入口和收敛研究设计，不恢复旧评测任务，不沿用旧模型预算发起新实验。任务域、数据许可、运行环境、模型和费用上限在试验前明确。

## 阶段与完成门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| R0 维护基线 | GitHub 历史快照、main、统一文档和代码入口 | 原状态可取回；独立内层仓库不变；文档与必要回归检查通过 |
| R1 任务与环境筛选 | 开发样本清单、复现命令、独立判据、资源估计 | 实际复现原故障，正常行为可检查；明确无法运行和排除原因 |
| R2 基线与失败分析 | 同一模型/工具下的基础修复轨迹 | 区分环境失败、证据不足、错误根因、实现错误及行为破坏；找出值得干预的实际问题 |
| R3 最小机制实现 | 假设分歧→执行检查→证据更新→补丁→失败后调整的闭环 | 机制改变实际读取、检查或候选；保持模型消息协议与共同预算 |
| R4 独立评测 | 冻结配置、多项目测试、必要消融、时间与费用统计 | 不依赖挑选成功样本；独立测试与搜索时反馈隔离；收益与损害可追溯 |
| R5 上游衔接与论文 | 缺陷发现到修复的交接实验、可复现材料、贡献说明 | 同时报告发现后条件修复率和全流程完成率；主张与证据一致 |

R1 可先考虑 12–20 个开发任务、覆盖 3–5 个项目。这是环境与机制试点的建议规模，不是已选择的数据，也不代替正式评测样本量。正式规模由任务可用性、试点方差和预算决定。

## 机制实现的取舍

优先围绕当前决策组织假设、支撑与反证、保留行为及失败原因；在有实质歧义时选能区分解释的检查；证据足够时允许直接生成补丁。现有 SQLite、记录对象、工具循环和执行适配继续复用。

不把图数据库、额外多 Agent 编排、自动 Skill 晋升或完整研究账本作为前置。它们只有在具体业务失败说明必要性之后才单独立项。现有扩展代码保留兼容，不因为研究方向调整就全部启用或宣称完成。

## 环境与数据选择

优先使用项目原有测试、可重建依赖和成熟隔离环境；需要容器时先核对单任务资源，避免全量下载大型镜像。Windows 作为当前开发入口，其他宿主与后端分别验证。

故障日志或 PoC 可以作为已知输入，前提是所有比较方法拥有相同信息。不得将参考补丁、隐藏检查、未来任务答案放进求解上下文。基准选择和最接近方法的代码复现属于 R1/R2，既有文献清单只是证据起点。

## 变更边界

迁移以外层仓库为唯一代码基线，`answer_B` 不参与同步。原开发快照分支和标签保持不变，main 的新提交不改写历史。包名、CLI 和旧 schema 暂保留兼容，后续若更名或精简接口，应以必要的安装、恢复和运行回归为一个完整变更处理。
