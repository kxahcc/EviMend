# 项目实施计划

状态：当前计划，尚未完成实施。最后维护：2026-09-17。
职责：维护阶段顺序、依赖和验收门槛。实际进度只在 [STATUS](STATUS.md) 维护；算法与接口分别见 [设计草案](development/system-design-draft.md) 和 [模块规格](design-contracts.md)，指标以 [评测口径](preparation/metrics-and-gates.md) 为准。

## 目标和当前推进方式

完成日志分析、根因行定位、补丁生成、实际运行验证和反馈自修复的完整系统，同时记录效果、功能回归及资源消耗。当前优先完成可实施的设计与离线软件自检，HarmonyOS 远程环境后续接入；设备可用不是继续设计的前提。

设计可以先确定算法步骤、数据对象、工具边界、控制器分支和验证义务。需要实测才能决定的是：策略是否有效、哪些案例可稳定复现、模型与预算如何取值，以及业务判据是否充分。当前不把这些待验证问题写成已证实结论。

## 阶段与依赖

| 阶段 | 工作范围 | 完成依据 | 环境依赖 |
|---|---|---|---|
| P0 设计闭合 | 单 Agent 动作协议、修复义务/反例关联、字段不变量、预算逻辑、四类规则与失败推演 | 一条正常路径和各失败路径都有输入输出、下一动作和停止条件；待定项明确列出 | 无需设备或模型实验 |
| P1 离线模块 | Deep Agents/Pydantic 隔离环境与依赖锁、对象校验、恢复、补丁目录、轨迹与规则组织 | 合成反馈能覆盖回退、未知、阻塞和预算耗尽，不误报成功 | Python 开发环境；不需要应用运行 |
| P2 执行条件 | 明确案例身份、业务判据、模型入口；接入完整工程、构建和目标回放 | 两个预登记代表应用的原始故障能复现，正常行为可被独立检查，运行版本可核对 | 实际模型入口及远程 HarmonyOS 环境；就绪后再开展 |
| P3 基础闭环 | 连接诊断、补丁、验证、反馈和资源统计 | 无人工接续地结束为成功或明确失败；至少一例有功能与回归证据的有效修复 | P1、P2 |
| P4 增强筛选 | 对修复义务绑定、诊断组织和决策相关检查做同预算对照 | 能指出新增成功、损害和成本来自哪项机制；无收益的模块可关闭 | P3 和冻结的评测输入/判据 |
| P5 覆盖与比赛交付 | 扩展案例、重复运行、冻结配置，按模板整理提交材料 | 使用说明可复现，完整尝试与各指标有来源，未解决案例没有被删除 | 已接纳案例的执行条件 |
| P6 论文扩展 | 依据实证收敛主张，补独立数据、近邻方法、消融和泛化 | 贡献可归因，结论不超出证据；比赛名次不代替研究结论 | 比赛阶段证据和新增数据授权 |

各阶段是工程条件，不要求每一步重新向用户申请确认。P0/P1 可持续推进；P2 的资源准备不阻塞它们。模型和应用实验仍按当前用户安排暂缓。

## P0 需要具体到什么程度

| 设计项 | 当前规格所在位置 | 进入实现前要补齐或审查的内容 |
|---|---|---|
| 诊断输入输出 | 模块规格第 1 节 | 可校验 schema、未知值与错误引用的实例；不要靠自然语言字段名猜类型 |
| 控制器 | 模块规格第 2 节、设计草案第 1.1 节 | SDK 工具/中间件约束接入、默认子代理关闭和内部调用计费；完整转换表、动作优先级、持久化/恢复边界及合成反馈序列 |
| 修复工作目录 | 模块规格第 1.3 节 | diff 应用/回滚的原子边界、失败恢复与产物绑定 |
| 四类规则 | 模块规格第 3 节 | 条件与数据绑定方式、触发/退出样例、业务语义未知时的处理 |
| 模型适配 | 设计草案第 1.1 节 | 提供方适配包到领域对象的请求/响应契约，格式错误、usage 和重试处理；实际模型待资源条件 |
| 远程后端 | 设计草案第 6 节 | HTTP 作业与请求/结果 schema、幂等/取消及子进程恢复；实际地址、SDK 和设备待远程资源 |

这些缺口主要是离线工程规格工作，不必等真实环境。规格审查和小型自检可以交替进行；不能因写了概念方案就宣称已经完成全部详细设计。

## 后续试验范围与调整规则

P2 先验收两个代表应用。P4 暂拟从已核查的六类代表机制选开发案例，B0/B1/P 各一次，最多形成首批 18 次完整求解；这是待接入条件核实的工程诊断规模，不是已登记任务清单，也不保证统计功效。组别和指标的唯一正式定义在评测口径文档。

输入不足、来源不明或环境不可运行的案例，在结果产生前登记处理规则。按应用/模板谱系划分开发与确认数据；重复日志、相似变体和重复运行不得增加独立样本数。后续规模依据可用独立案例与开发效果重新确定，不能沿用已归档的公开基准默认预算。

增强无收益时优先保留更稳的基础闭环。时间不足时先缩减新增机制，保住输入适配、验证、自动终止与交付能力；截止时间未知，因此不承诺具体完成日期。确认集运行前锁定主要指标、比较配置与停止规则。

## 交付与修改范围

开发方案写入开发设计和规格，正式提交阶段才填写 README.md、technical-design.md 和 test-report.md 模板。源代码、测试和标准化 Skill 按模板目录交付；运行结果进入 runs，必要的脱敏、可复现证据经筛选后再形成受跟踪报告。当前没有真实任务成绩，不能预填提交报告。
