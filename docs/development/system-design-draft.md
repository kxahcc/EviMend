# 应用软件代码故障精准定位与自修复：开发设计草案

版本：v0.2，2026-09-16。状态：设计稿。当前实现仅包含离线输入快照、日志解析与栈位置映射原型；模型诊断、自动修复、控制器和远程运行尚待实现。本阶段按用户安排先完成分析设计，不开展应用、设备或模型修复实验。

## 1. 核心决策

采用一个主控制器组织模型和工具。基础模型负责理解代码与生成候选，确定性程序负责证据引用、版本、预算、状态及运行结果的校验。模型参数训练后置，先用标准化约束知识和 Skills 提升决策质量。

核心方法为 **从运行错误提取约束，沿相关源码追踪约束被破坏的原因，再用验证反馈选择下一步修复动作**。原有 Agent 循环及结构化诊断方法是可复用基础；约束如何影响定位、候选选择和验证调度是我们拟检验的增量设计。

明确区分三个位置：

- **异常位置**：执行某个操作时发生错误的位置，通常来自栈。
- **根因位置**：使该操作所需条件被破坏的数据产生、状态更新或控制逻辑位置。
- **修复位置**：能够恢复预期行为的修改位置，可能存在多种合理选择。

栈命中不是根因预测，补丁落点也不自动等于根因。定位评测采用独立标签；功能正确性采用行为证据。

## 3. 核心方法如何执行

### 3.1 先建立可核对的证据

解析错误名称、消息、栈和日志来源，保留原始字节哈希与解码告警。源码映射按精确路径、大小写归一、路径后缀、唯一文件名逐级尝试；存在多个匹配时保留歧义。框架帧只从主候选视图中降权，原始记录保留。

每一条诊断依据必须引用日志行或源码范围。程序检查引用是否存在、版本是否一致；这仅证明引用有效，不能证明模型的因果解释正确。

### 3.2 从错误操作提出约束

错误消息用于缩小约束类别，实际操作及上下文决定适用条件。初版优先覆盖下表；其他错误走通用分析流程，不能为套规则而强行分类。

| 类别 | 可提出的运行条件 | 必须继续确认的业务含义 |
|---|---|---|
| 空对象/生命周期 | 使用时对象已初始化，当前路径能到达初始化 | 应该补初始化、等待异步结果，还是允许缺省结果 |
| 索引与长度 | 0 ≤ index < length，长度为合法整数 | 错误索引如何产生；直接截断、跳过或返回是否改变功能 |
| 字节/元素关系 | offset + count × width ≤ byteLength；TypedArray 的字节偏移还须按元素宽度对齐，DataView 读取不要求这种对齐 | 宽度、编码、尾部数据以及输出格式应是什么 |
| TypedArray 整段视图 | 使用整个 buffer 时，字节长度应满足元素宽度要求 | 业务是否本来应该按字节处理，尾部是否必须保留 |
| 递归/关系遍历 | 终止条件可达，关系环不会造成无限调用 | 是否允许重复节点，输出顺序如何定义；路径去重与全局去重不同 |
| 动态正则/解析 | 构造结果语法有效，输入符合所需格式 | 输入本来是字面文本还是正则；合法语法仍可能改变查询语义 |

约束状态分为 supported、contradicted、unknown，同时记录支持层次：日志观察、源码推断、局部执行或应用执行。没有观察到某路径不等于该路径不可能发生；某条事实成立也不等于整个根因假设成立。

### 3.3 在相关源码中追踪原因

从异常操作涉及的值开始，按需读取：本函数赋值/分支、传入参数、直接调用者、相关初始化与模块导出。模型提出需要补看的符号，检索工具提供有限片段，程序校验文件/符号/行号。

初版采用按需读取形成的局部关系记录，不预建整个应用的精确数据流图。关系记录包含“值来自哪里、受哪个条件控制、由谁消费”，并标注哪些联系是模型推断。轻量检索无法正确处理 ArkTS 语法时保留 UNKNOWN，不能宣称拥有完整静态分析能力。

初始配置建议一次保留最多 3 个根因候选、每轮扩展最多 6 个新文件、最多 2 轮扩展；这些是待校准的工程上限。上下文和时间预算先到就停止扩展，返回剩余未知事项，不把截断搜索当成排除了其他根因。

候选比较依次考察：是否与现有观察矛盾、能否解释异常条件如何被破坏、是否有可核对的输入到故障链、能否形成可检验的预期。模型自报的数值置信度不作为可靠概率。

### 3.4 生成保留行为的补丁

补丁生成器接收候选根因、相关代码、约束和已知预期行为，输出实际 diff 及四项说明：恢复哪个条件、保留哪个业务结果、会影响哪些行为、用什么检查能够反驳该修复。

候选在任何专属检查之前获得序号和哈希。第一候选局部检查失败，也必须保留为首次失败。不得删除测试、放宽断言、跳过目标动作或通过取消功能获取成功。

修复优先修改造成不合法状态的生产/更新逻辑；必要的防御检查可以作为补充。是否采用边界保护、转换数据格式或重建流程，应由业务要求决定，不能规定所有越界都采用 clamp、所有空值都采用可选链。

### 3.5 设计示例：字符数量与字节容量

以已静态阅读的 HouseholdService 022 为设计例：栈指向 Uint16Array(buffer, 0, payload.length)；上游 ArrayBuffer 只分配了 payload.length 个字节。对于长度为 N 且 N > 0 的情况，N 个 16 位元素需要 2N 字节，容量与视图要求不一致。

因此，应记录“视图创建行”为异常位置，“分配容量及视图构造之间的不一致”为根因假设。候选可以调整容量，也可以改用按元素数分配的视图构造方式；最终选择取决于 buffer 的其他消费者和校验行为。应验证创建与校验的结果一致、正常数据可处理、边界数据行为正确。

此例说明无需设备就能细化机制和验证义务，但不代表已经生成并验证了有效应用补丁。本设计文档包含案例分析，不属于未来盲测求解器输入。

## 4. 模块之间传递什么

所有对象带 schema_version、task_id 和 source_snapshot_sha256。运行记录另带 run_id；位置保存原源码坐标，候选修改后的坐标单独表示。

| 对象 | 必要内容 | 不允许混淆 |
|---|---|---|
| Task | 允许输入、源码/日志哈希、可用能力、预算、评测协议标识 | 源码路径对应不等于运行版本一致 |
| Evidence | 来源类型、来源哈希、行范围/运行标识、观察内容、观察或推断 | 源码引用不能伪装成执行结果 |
| Diagnosis | 异常位置、候选根因位置、约束、生产者/消费者关系、证据和未知项 | 根因与修复落点分开 |
| CandidatePatch | 尝试序号、父快照、diff 哈希、修改意图、影响范围、行为义务 | 未生成候选和生成后失败均要留痕 |
| VerificationPlan | 要验证的假设、运行层次、输入类别、预期行为来源、所需能力 | 模型临时自测和独立验收测试分开 |
| VerificationResult | 每层状态、观察、错误类型、产物哈希、耗时与执行版本 | not_run、blocked、inconclusive 都不能记为 pass |
| Attempt | 采用的诊断、候选、检查、实际成本、下一步动作及理由 | 回退保留此前成本与尝试 |
| FinalReport | 初始/最终定位、最终补丁、终止状态、覆盖与未知、全成本 | 离线分析完成不等于任务修复完成 |

验证结果统一使用 pass / fail / not_run / blocked / inconclusive。任务终止状态使用 verified_under_protocol / unresolved / blocked / budget_exhausted；verified_under_protocol 只表示通过指定协议覆盖的检查，不表示未来永不出错。该状态还要求原始版本在相同目标协议下确实触发故障；原故障未复现时，不能仅凭补丁版本不崩溃宣称修复成功。

## 5. 控制器与自动再修复

主控制器维护状态，不由模型随意宣布完成。基本流程如下：

~~~text
整理证据，提出候选根因
在预算允许且仍有新动作时：
    生成并登记一个完整候选补丁
    检查 diff，并执行可用的局部检查
    若不满足关键约束：记录失败，更新候选
    若需要的远程能力未接入：保存验证计划，结束为 blocked
    否则构建并运行目标、行为、回归与必要复跑
    若所有必要层通过且版本相符：接受候选
    否则分类反馈，选择修补、重定位、回退或结束
输出所有实际尝试及未知项
~~~

关键动作表：

| 观察 | 下一步决策 |
|---|---|
| 补丁引入类型/编译错误 | 在现有诊断下修正代码；原始环境错误另行分类 |
| 原异常仍存在 | 先核对本轮源码、安装产物与操作，再检查诊断/修改是否触达原因 |
| 新异常或行为回归 | 恢复到记录的父快照，将违反的行为条件加入下一候选输入 |
| 设备/导航失败 | 有界恢复环境，不以此证明根因错误，也不盲目改业务源码 |
| 候选产生相同 diff 和同样失败 | 检测空转；选择新假设或停止 |
| 有效反例推翻诊断 | 标记对应假设被反驳，保留证据后重定位 |
| 所有必要层通过 | 锁定补丁、产物和验证记录，完成 |

初版暂定每任务最多 3 个完整候选、额外诊断探针最多 1 次，受统一 Token 和墙钟上限约束。调用前预留该调用输出上限与剩余必要步骤的预算，调用后以实际 usage 记账；未获得的费用字段为 null。缺少价格配置时只执行已配置的 Token/调用数/时间限制，不虚报精确费用限制已生效。

额外探针只用于区分会导向不同修复的候选解释。无可用执行能力时可以改做源码证据补查；不能捏造运行观察。重试模型、补丁生成失败和环境恢复开销都计入。

## 6. 本地分析与远程执行的接口

核心逻辑不绑定 SSH、HTTP 或具体云厂商，先依赖统一 ExecutionBackend 协议。日后根据实际远程环境实现传输层。

| 接口 | 作用 |
|---|---|
| describe() | 返回 SDK、设备/模拟器、构建与测试能力、允许的执行层次和并发限制 |
| submit(request) | 提交版本绑定的构建或测试任务，返回 job_id |
| poll(job_id) | 返回排队、运行、完成或失败状态以及结构化结果 |
| cancel(job_id) | 请求停止；取消请求发出不等于已停止 |
| fetch_artifact(reference) | 取得构建日志、设备日志或结果，核对哈希 |

ExecutionRequest 必须绑定 task_id、完整运行源码哈希、补丁哈希、环境标识、测试协议哈希、初始状态方案、执行层次、重复序号和超时。幂等标识只对这些字段完全相同的一次逻辑调用有效；重跑使用新重复序号，不能错误复用历史成功。

远程适配器接受经过配置的任务类型，如构建、安装、目标回放和行为测试；协议不要求模型拥有任意远程终端访问。签名及设备凭据放在执行端配置中，不进入模型上下文。

目前无远程环境，describe() 对执行能力应报告不可用，应用验证维持 not_run/blocked。可以先检查请求字段及控制器对这类结果的处理；模拟后端仅用于软件自检，不能产生应用成功成绩。

## 7. Skills 的具体位置

一个 Skill 对应一类可迁移的诊断/修复动作，而不是某个案例编号。标准结构包括：适用特征、必需输入、需要成立的约束、查证步骤、可选修改、禁止破坏的行为、验证义务、退出与回退条件。

首批拟设计初始化顺序、索引/字节边界、递归终止、动态正则四类。约束知识集中维护，Skills 引用它们，避免提示、代码和文档维护多份不一致规则。静态检查失败、局部运行失败和应用回放失败分别进入反例记录。

通用 Agent 仍拥有相同工具权限；Skills 的增量是组织证据和选择动作。未匹配 Skill 时走通用流程。开发阶段的经过验证经验可以用于修订 Skills，最终评测配置冻结，不在线吸收隐藏答案。

## 8. 如何让设计贡献能够被验证

需要检验的主张是：在同模型、同工具、同总预算和同最终验收条件下，约束诊断与反馈策略能否提高有效修复，或以更低消耗维持质量。当前是方法假设，尚无实测结果。

- B0：完整基础 Agent，直接使用日志、源码和工具。
- B1：增加结构化诊断交接。
- P：进一步加入约束追踪和反馈驱动的验证选择。

诊断约束和验证策略可分别关闭，用于区分收益来自哪里。额外实验在远程环境和评测协议就绪后开展。当前小规模数据主要适合工程诊断；正式论文需要充分的独立案例与近邻方法比较。

来源与借鉴范围沿用 [相关研究记录](../preparation/prior-art.md)：结构化诊断、运行证据和 Agent harness 均有成熟先例。本工作定位为这些方法在当前任务上的可量化改进，不把“使用约束/验证/Skills”本身当作首创。

## 9. 没有设备时如何推进，何时设计算到位

当前优先完成三类可审查产物：

1. **方法规格**：用代表案例逐条推演输入证据、约束、候选、合理修复和反例，检查机制是否自洽；不将推演写成实验结论。
2. **模块与协议**：固定上述数据对象、失败类型、状态转换及后端请求，明确离线与运行工程的区别。
3. **实现清单**：标出每个模块依赖、输入输出、待实现功能和自检条件，后续编码按依赖推进。

设计验收要求：异常点与根因点不同的案例能表达；未知约束能保留；相同错误可有不同业务修复；失败可以触发合理新动作；设备缺失不会误判成功；首次尝试与全部成本不会丢失。当前设计已覆盖这些路径，真正的效果和阈值仍留待后续环境验证。
