# 应用软件代码故障精准定位与自修复：开发设计草案

状态：当前设计草案，尚未全部实现或实测。最后维护：2026-10-06。
职责：维护架构、核心算法及后端抽象。实现状态见 [STATUS](../STATUS.md)，字段与规则见 [模块规格](../design-contracts.md)，阶段见 [实施计划](../project-work-plan.md)。

## 1. 核心决策

采用一个主控制器组织模型和工具。基础模型负责理解代码与生成候选，确定性程序负责证据引用、版本、预算、状态及运行结果的校验。当前路线不微调模型；领域 harness 围绕修复义务组织上下文、经验和 Skills，具体设计及未实现边界见第 7 节。

核心方法为 **从运行错误提取约束，沿相关源码追踪约束被破坏的原因，再用验证反馈选择下一步修复动作**。原有 Agent 循环及结构化诊断方法是可复用基础；约束如何影响定位、候选选择和验证调度是我们拟检验的增量设计。

明确区分三个位置：

- **异常位置**：执行某个操作时发生错误的位置，通常来自栈。
- **根因位置**：使该操作所需条件被破坏的数据产生、状态更新或控制逻辑位置。
- **修复位置**：能够恢复预期行为的修改位置，可能存在多种合理选择。

栈命中不是根因预测，补丁落点也不自动等于根因。定位评测采用独立标签；功能正确性采用行为证据。

### 1.1 产品形态与技术栈

目标交付是支持单任务与批处理的代码故障定位与自修复 Agent，命令行是启动入口。输入为日志、源码和允许的执行入口，输出为根因位置、可应用补丁、验证记录和资源报告。模型负责选择动作，执行框架负责调度与保存状态，我们实现修复策略及验收适配。

**首版采用 Python 3.13 + Deep Agents SDK（底层 LangGraph）+ Pydantic 2 + langchain-core + SQLite；应用构建、设备回放和评测在用户本机通过受管作业进程执行。** 项目专属 Python、SDK 依赖和 SQLite 检查点已由 uv.lock 锁定；固定响应、模拟模型请求与 HTTP 模拟作业协议已接入，真实云端传输、工具链作业适配和应用验收控制仍待实现。基础模型拟由本机 Agent 调用云端大模型 API，不部署本地权重；具体提供方和型号仍待选定，不假定有远程应用执行主机。

#### 选型依据与替代方案

直接使用 LangGraph 需要我们补通用代码工具、上下文管理和 Agent 循环，首版工程量偏大。主实现选择 **Deep Agents SDK**，LangGraph 保留为其底层运行时；复用工具循环与扩展点，我们实现受控文件工具、领域策略、候选管理和应用验证。SDK 的自动压缩及文件卸载显式关闭；可选的主机压缩在模型发送边界完成，采用独立产物、统一费用账本和恢复协议。合成切片只证明这些接口能组合，不证明本项目的修复效果。

| 方案 | 适合之处 | 本项目取舍 |
|---|---|---|
| Deep Agents SDK | 提供文件工具、上下文管理、Skills、可扩展工具和中间件，底层沿用 LangGraph | 当前优先接入；先用合成检查核验约束、恢复与计费，不自行重写通用 Agent 循环 |
| Claude Agent SDK | 提供 Claude Code 的工具、循环、上下文及 hooks，可接自定义工具 | 若确定使用 Claude，是快速落地的有力选择；当前模型资源未定，优先保留跨提供方能力 |
| mini-swe-agent | 简洁的代码修复循环，便于理解与改动 | 外部基础参照；若主框架适配负担过重再评估替代，不同步维护两套主引擎 |
| LangGraph Graph API | 显式状态和分支，控制自由度高 | 作为 SDK 底层能力；首版不自行搭建完整节点图 |
| PydanticAI / 手写循环 | 类型化工具或极简循环可控 | 不作为当前主线，避免继续承担通用 coding harness 的组装工作 |

依据为官方 [Deep Agents 概览](https://docs.langchain.com/oss/python/deepagents/overview)、[定制接口](https://docs.langchain.com/oss/python/deepagents/customization)、[后端说明](https://docs.langchain.com/oss/python/deepagents/backends)、[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 和 [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)，本次查阅日期为 2026-09-17。没有以其他基准的成绩推断 HarmonyOS 效果。

首版一个主 Agent，不部署云端托管平台、Redis、Celery 或 Kubernetes。SDK 自带子代理不代表需要启用多 Agent；锁定版本的固定响应切片已用 `HarnessProfile` 显式关闭通用子代理并核对未向模型提供 `task` 工具，不能只假设 `subagents=[]` 足够。升级 SDK 时必须重跑此检查。

#### 模型与策略如何解耦

SDK 维护模型消息和工具循环；工具边界转换为我们自己的 ActionProposal/ModelObservation，业务策略不依赖 AIMessage 内部字段。优先使用原生工具调用，返回后再做本地 Pydantic 校验。供应商格式约束不能代替业务校验，格式修复同样记为模型调用。

只由一层负责语义重试和预算，关闭或显式计入 SDK 的自动重试；不允许 SDK、图节点和控制器各重试一轮却只记录一次。`ModelCallStore` 已接入固定响应及模拟请求模型，覆盖调用前登记、Graph 落盘前的完整响应回放、未知发送停止、格式错误和 usage 分类。`PreparedRequest` 以唯一规范化 JSON 发送体固定消息、工具、参数及 profile 哈希；实际发送前重核，不能只给发送前另一份对象留指纹。SDK 的中性 `tool_choice=None` 由模型入口省略，其余不支持字段明确拒绝。

当前 Chat Completions 边界只允许进程内 MockTransport 和固定无网络端点，不接收密钥；配置固定模型标识、输出上限、温度与超时。文本、工具调用和显式 reasoning_content 有限支持；附件、流式响应、未声明选项或不完整工具调用不静默降级。混合有效/无效工具调用的整个响应停止，不执行其中有效子集。原始 usage 保存，合法计数另做归一化；缺失/错误用量保持未知，已知 Token 预算只阻止下一次发送，不能保证当前响应或真实计费硬上限。该协议参考 [DeepSeek Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)，查阅日期 2026-10-02；这不是已选择 DeepSeek 或已验证其真实兼容性。

真实适配时，求解、格式修复、上下文压缩及 SDK 重试均须穿过同一计数边界；提供方底层隐式重试必须关闭或逐次计入。原始响应中可获得的 usage/请求标识保留，适配器不支持的字段保持未知，不静默删除后称计费完整。确认的格式、usage、上下文和工具能力写入模型配置；具体模型账号和型号不是框架选择的前提。

上下文策略保持显式有界：通过 HarnessProfile 关闭 SummarizationMiddleware，并通过公开同类中间件替换关闭 FilesystemMiddleware 的人类消息/工具结果卸载；保留必需文件中间件及原工具排除。默认不压缩，超过序列化消息字节上限以 context_limit 停止。可选 CompactionPolicy 在调用边界按字节触发，保留 system、启动任务和近期完整工具组，把较早的闭合前缀归纳成带来源范围的模型推断；Graph 原历史始终保留。摘要无工具、不共享求解模型的工具绑定，以 context_compaction 用途进入同一预算和恢复账本；冻结来源、摘要及实际发送视图只写受管 work/compactions。摘要完成但 Graph 未保存可回放，未知结果不重发，格式失败仍计费。参数由 context_compaction.py 定义，发送视图硬限额由 models.py 定义；context_profile 和模型配置在 session 冻结，基础/增强一致。首版重新摘要完整历史前缀，摘要输入或必须保留的尾部超限时明确停止；尚无滚动摘要或无限历史能力，字节限额也不代表云端 Token 窗口。依据 2026-10-02 对锁定 SDK 0.7.18 本机源代码的检查，默认摘要调用带重试的模型并写 backend，默认大工具结果也会卸载，因此保留关闭策略。详细约束见模块规格第 1.2.2 节。

#### 持久化不能替代外部操作一致性

检查点恢复可能重新执行未完成节点。补丁应用、本机作业提交、模型调用分别是独立动作边界，先登记稳定 action_id，再执行并保存结果。本机作业用幂等键找回原 job_id，恢复时核对进程身份、设备状态和产物；补丁节点核对候选目录内容，不重复累积修改。模型账本保留完整响应以跨越“提供方返回、Graph 尚未保存消息”的窗口；若发送后本地未保存响应，同 ID 不再发送，结果/费用为 unknown。进程崩溃而模型服务已处理请求的窗口无法普遍保证 exactly-once，不能直接当作未花费。

首版按任务串行执行会改变源码或设备状态的动作，一台设备同一时刻只有一个运行任务。SQLite 检查点与领域事件记录不承诺跨库原子提交；恢复时根据 action_id、版本和产物对账。恢复测试要覆盖“外部操作成功但本地尚未写完记录”的窗口。图重放是调试能力，不代表再次执行的模型结果相同，也不是可复用的独立评测成绩。

#### 依赖接入门槛

W03–W06 已完成不调用真实模型、不连接设备的离线接入切片。下列四项是正式实现仍须保持的门槛；固定响应循环覆盖受控读写、候选登记、失败修订、usage 汇总和 SQLite 重开，模拟 HTTP 协议覆盖作业幂等与响应丢失恢复的合成语义。完整业务对象、真实模型请求计费和本机设备状态核验尚未覆盖：

1. 固定响应能驱动读取、编辑、候选登记、检查失败和继续修复，领域对象能严格校验。
2. 文件编辑只产生工作副本变更；run_check 必须先冻结并登记实际 diff，绑定不可变 candidate_id。任何可执行修改后代码的通道都走同一登记门，不开放可绕过该门的任意 shell；检查期间不得修改被测快照。自定义工具不能取消原有通用检查能力。
3. 主循环、上下文压缩、格式修复、SDK 重试等调用全部进入预算；默认子代理禁用，工具与模型调用记录可导出。基础/增强组使用同一套框架配置，不能把默认能力差异算成算法收益。
4. SQLite 恢复及本机作业不重复累积补丁，不错误重复执行，也不能在未运行检查时宣称成功。

内置 FilesystemBackend 只是一种文件访问后端，不是系统级沙箱；使用任务根目录和虚拟路径限制，应用执行另由受管本机进程承载。文件后端不会自动提供 HarmonyOS 的构建、设备和业务验收能力，仍由我们的 ExecutionBackend 实现。

若这些边界需要大范围修改 SDK 源码才能满足，就不继续加框架补丁；回到本节比较的轻量主循环方案评估。先使用公开工具/中间件扩展点，不 fork SDK，也不并行实现备选引擎。

当前 uv.lock 由受管 uv 0.12.9 解析，记录 Python 3.13.5、Deep Agents 0.7.18、Pydantic 2.13.5、SQLite checkpoint 3.1.1、HTTPX 0.28.1、FastAPI 0.141.1、Uvicorn 0.54.0 等依赖；使用 `uv sync --locked`。升级任何框架依赖需重跑受影响的固定响应、恢复及质量检查。锁定语义见 [uv 文档](https://docs.astral.sh/uv/concepts/projects/sync/)。

#### 执行来源怎样冻结与恢复

每个新 run 在创建工作区前保存主机实际来源，避免后来只凭当前 Git 或依赖锁猜测当时运行了什么。provenance.py 记录受限执行源码清单、项目/锁/运行资源配置的原字节哈希、实际 Python 与已安装 distribution 元数据，Git HEAD/dirty 则作为独立的初始观察。文档与测试不属于执行源码清单，Git-only 变化不会单独阻止续跑；运行源码、锁或实际环境变化须拒绝。清单、兼容身份、完整记录分别有自洽摘要，准确字段以 [模块规格第 1.2.2 节](../design-contracts.md) 为准。

标准命令入口先在导入 CLI 前建立源码基线并在导入后复核；Agent 在开始及结束边界核对兼容身份。无知识运行的 session/report/completion 为 10/7/4，主机批准知识的普通运行为 11/8/5，显式三态策略启停两组为 12/9/6，固定初始来源、工作上下文及相应知识身份，从保存记录重建实际发送与工具使用。知识 startup 的程序参数为 knowledge=HostKnowledgeInput；恢复只接受原 knowledge_approval，显式三态运行还须提供相同 applicability_policy；从 session 固定身份及 run 原件核验知识，不再复制外部库。续跑只读预检先于可写账本和 Graph，mock offset 也只读；已知查询漂移或账本不能认证已有查询时拒绝可写恢复。准入拒绝使用退出码 3，让工作进程保留已有终态；获准执行后的失败仍保留失败记录与成本。旧 session/report/completion 8/5/2 与 9/6/3 只能按原契约回读，分别保留未知来源与已保存来源，不自动升级或续跑。聚合及私有包核验检查保存来源，不要求等于读者当日 Git/环境，也不补写旧运行版本。

这些记录是文件与版本元数据的观察，不是文件锁、签名、全依赖二进制校验或内存执行认证。主机源码清单仅存路径/大小/哈希，不自动复制未提交源码 diff 或运行环境，因此私有证据包不能单凭来源清单重建主机修改。W08 正式比较还要保全可重建的主机代码与环境材料，并另行绑定真实工具链、完整应用、设备和共同协议；当前实际软件验收只记 STATUS。

### 1.2 实现切分与第一版 Agent 工具

沿用现有输入证据代码；W04–W07 已建立离线闭环、模拟 HTTP 协议和策略分支，下表区分已有能力与目标职责：

| 模块 | 负责什么 | 复用边界 |
|---|---|---|

任务指引要求从异常用点追查赋值、分配、参数、调用者、分支/回调顺序和消费者，再提交原始行的根因假设与最小保行为修法。直接修复无需强行制造多个假设或条件检查；未知输入允许有说明的尽力候选。失败后依据实际反馈分别修订代码、重审上游原因或报告环境/结果未知，而不是无限重试。指引是一项共享任务能力；规则、义务和决策相关检查是可关闭的增量。检索工具按路径和行稳定分页，明确编码跳过与片段截断，主机核验源码哈希，并使用相同 read_source 能力和工具预算。具体字段及续跑冻结见模块规格第 1.2.4 节；现有脚本自检不证明模型会自主执行这些步骤。

固定响应与 W04 工作区已在 W05 组成离线调度，W06 以模拟服务核验作业协议，W07 又接入可关闭的规则与动作建议。实际模型能否正确提出修法、应用业务反馈能否改进下一轮，仍须在本机真实实验阶段核验。已装好 SDK、能生成 diff、能调用模拟 HTTP 分别是工程接入证据，不等同于有效修复。

分析快照与运行工程分开：前者只包含允许分析的源码/配置和选定日志；后者必须保留完整构建所需资源、依赖及经过适配的测试入口。显式 schema 2 案例目录由准备者填写谱系、故障变体、唯一日志成员和可选场景脚本哈希；`prepare` 核验原字节，任务快照只携带选择摘要，不复制评测脚本。当前 analysis_source_v1 会排除图片等运行资源，不能拿它直接编译应用；目录核验不证明源码与日志来自同一次构建。

在进入真实运行前，独立准备者为明确的“应用谱系组 + 故障变体 + 日志原字节 + 源码版本”建立候选无关的共同验收协议。模型只提出动作和补丁，主机核对引用、能力、预算和停止条件；真实执行适配器登记结果；接受门检查原版目标故障确实出现、候选修复及业务/回归结果的版本和协议一致性。模型预测与合成检查不能转写成应用执行证据。字段和拒绝条件见 [模块规格第 1 节](../design-contracts.md#1-数据契约与不可破坏的条件)。

## 3. 核心方法如何执行

### 3.1 先建立可核对的证据

解析错误名称、消息、栈和日志来源，保留原始字节哈希与解码告警。源码映射按精确路径、大小写归一、路径后缀、唯一文件名逐级尝试；存在多个匹配时保留歧义。框架帧只从主候选视图中降权，原始记录保留。

每一条诊断依据必须引用日志行或源码范围。程序检查引用是否存在、版本是否一致；这仅证明引用有效，不能证明模型的因果解释正确。

### 3.2 从错误操作提出约束

错误消息用于缩小约束类别，实际操作及上下文决定适用条件。方法涉及下表约束类别；具体规则以模块规格为准；其他错误走通用分析流程，不能为套规则而强行分类。

| 类别 | 可提出的运行条件 | 必须继续确认的业务含义 |
|---|---|---|
| 空对象/生命周期 | 使用时对象已初始化，当前路径能到达初始化 | 应该补初始化、等待异步结果，还是允许缺省结果 |
| 索引与长度 | 0 ≤ index < length，长度为合法整数 | 错误索引如何产生；直接截断、跳过或返回是否改变功能 |
| 字节/元素关系 | offset + count × width ≤ byteLength；TypedArray 的字节偏移还须按元素宽度对齐，DataView 读取不要求这种对齐 | 宽度、编码、尾部数据以及输出格式应是什么 |
| TypedArray 整段视图 | 使用整个 buffer 时，字节长度应满足元素宽度要求 | 业务是否本来应该按字节处理，尾部是否必须保留 |
| 递归/关系遍历 | 终止条件可达，关系环不会造成无限调用 | 是否允许重复节点，输出顺序如何定义；路径去重与全局去重不同 |
| 动态正则/解析 | 构造结果语法有效，输入符合所需格式 | 输入本来是字面文本还是正则；合法语法仍可能改变查询语义 |

约束状态分为 supported、contradicted、unknown，同时记录支持层次：日志观察、源码推断、局部执行或应用执行。没有观察到某路径不等于该路径不可能发生；某条事实成立也不等于整个根因假设成立。首批有限检查只对主机固定的合成标量输入计算谓词，结果的 satisfied/violated 描述这些输入，不能自动改变假设状态。记录绑定输入指纹、诊断和源码范围；固定响应 Agent 可回读并在相同范围下引用，开启关联时只建议重审相关方向。算子/角色/候选坐标的适用性仍是推断，条件满足不确认业务通过。字段、恢复与来源边界见 [模块规格第 3.0 节](../design-contracts.md#30-首批有限条件检查)。

#### 3.2.1 怎样取得可信的条件输入

**先确认“哪一个操作的哪一个参数”，再取得值，最后计算条件。** 当前已有独立的原字节核验、主机合成绑定与采值凭据登记；实际语法/类型解析、源码 literal 提取、运行采样和新来源计算仍待实现。完整路径用于减少参数误配和旧版本反馈的误用，不取代模型理解业务或共同验收；无法确认时，Agent 仍能沿通用读代码、改代码和检查路径继续。

例如，容量为 4 字节、偏移为 8 字节、元素数为 0、宽度为 2 时，8 + 0 × 2 ≤ 4 不成立；调换容量和偏移会错算成 4 + 0 × 2 ≤ 8 成立。两者单位相同，所以还要核对参数在实际操作中的角色。这个例子仅说明绑定问题，不是应用运行结果。

```mermaid
flowchart LR
    A[模型提出操作和待查参数] --> B[主机核对源码锚点与参数角色]
    B --> C[读取有限源码事实或取得受管采样凭据]
    C --> D[核对版本 对象 操作事件与前提]
    D --> E[有限条件计算]
    E --> F[保留来源与适用性后交给修复决策]
    B --> U[证据不足 保留未知并允许通用修复]
    D --> U
```

| 层 | 具体工作 | 首版实现边界 |
|---|---|---|
| 操作绑定 | 把有限算子、参数角色和诊断绑定对应到精确源码位置；容量、偏移、宽度各自有依据 | Python/Pydantic 已有独立合成契约及原字节/父操作核验；角色含义来自主机 fixture，不能凭名称、行号或单位确认真实 API |
| 源码采值 | 读取已定位参数槽上的有限整数 literal，记录它在源码中确实出现 | 不执行表达式，不传播变量初始化值，不把文本常量当作实际使用点状态；复杂语法返回未知 |
| 运行采值 | 从同一次实际操作取得参数、对象和状态，绑定受管作业与运行产物 | 依赖 W08 的本机适配器；只支持经验证不会重复求值或改变调用顺序的采样方式，当前不开启 |
| 条件计算 | 根据已登记输入计算谓词，分别报告计算、来源、操作绑定和平台适用性 | 数学结果可有结论而运行适用性未知；局部结果不自动确认根因、业务或稳定性 |

源码入口使用现有 Python 标准库和严格对象校验处理原字节片段；独立合成入口不引入解析依赖，也不提供真实解析资格。主机配置固定 adapter/profile，绑定、采值请求及动态凭据各自追加登记；恢复需要同一可信配置和历史 fixture，回读不新建记录。后续源码提取器只支持明确的有限操作形状和直接整数 literal。源码中的 `const n = 4` 只证明初始化文本；没有已实现的数据流规则时，不断言使用点 n 的值。内置构造器遮蔽、包装函数和同一行多个调用都可能使名称/行号匹配失效，缺类型或作用域依据时保持未知。完整 ArkTS 前端/类型解析器不列为此包前提，其适配选择在实际工具链盘点后确定。

候选须按新字节重新建立操作绑定；旧行号、相同片段或 diff 的近似映射只能帮助搜索，不能给出唯一采样点。运行入口还须把原始运行版本、插桩后的观察版本和探针配置分别绑定。采样使用本次操作已取得的值，禁止为记录再次求值 getter、函数或转换表达式；适配器不能证明这一点时不给运行值资格。

完整接口是 `bind_operation(proposal) → BindingAssessment`、`capture_values(request) → CaptureReceipt`、`calculate_condition(binding_id, receipt_ids) → ScopedConditionResult`；最后一步尚未接入新来源，前两步的当前 Python 接口须由主机另供合成 fixture，未成为 SDK 工具。模型只提出位置、问题和已有 ID，主机产生绑定及凭据；字段、来源分层、拒绝/未知反例和旧 schema 迁移统一见 [模块规格第 3.0.1 节](../design-contracts.md#301-可信采值与算子绑定)。来源读取与实际探针的开销都计入共享预算，基础/增强有相同采值能力。可信采样只是诊断输入，不提供免费的测试或更宽的应用接受条件。

### 3.3 核心机制一：把根因假设转成可检查的修复义务

Agent 不只输出一句原因，还维护一份紧凑的任务工作记录：异常操作、相关值的来源、被破坏的条件、候选根因、必须保留的业务行为，以及尚未查明的事实。这里把“补丁必须恢复的条件与必须保留的行为”统称修复义务；它们有证据来源和状态，不是把模型推测包装成正确需求。

处理步骤：

1. 从异常操作涉及的值开始，按需读赋值、分支、参数、直接调用者和消费方，形成局部关系链。每条边标注源码事实或模型推断，不预建完整程序数据流图。
2. 绑定规则参数，例如 buffer 容量、元素宽度、元素数；记录运行条件与业务条件。能机械检查的条件进入检查器；无法执行的语义要求保留为未知。
3. 形成不同的根因解释和对应修复方向。如果两种解释最终要求同一修复、相同验收，就无需为它们分别消耗探针。
4. 对会导致不同修法的未知事实，记录一个区分问题，以及可能观察结果分别支持什么动作。检查未区分候选时保留不确定性。
5. 补丁引用其恢复的义务，并说明保留的输出/状态/顺序。失败反馈更新相应义务和假设，而不是向整个对话无差别追加日志。

初始配置建议最多保留 3 个根因候选，每轮最多扩展 6 个新文件、最多 2 轮扩展，均为待校准上限而非必须用满的配额。直接、完整的解释可以只有一个候选。通用路径不强行套入四类规则；未知语法、跨模块来源与无法解析的调用关系必须显式保留。

预期作用是让定位、改代码和检查围绕同一组问题衔接：定位发现的业务条件不会在生成补丁时丢失，运行反例能明确推翻具体前提。这是待检验机制，不能凭工作记录格式规范就认定因果解释正确。

### 3.4 生成保留行为的补丁

补丁生成器接收候选根因、相关代码、约束和已知预期行为，输出实际 diff 及四项说明：恢复哪个条件、保留哪个业务结果、会影响哪些行为、用什么检查能够反驳该修复。

候选在任何专属检查之前获得序号和哈希。第一候选局部检查失败，也必须保留为首次失败。不得删除测试、放宽断言、跳过目标动作或通过取消功能获取成功。

修复优先修改造成不合法状态的生产/更新逻辑；必要的防御检查可以作为补充。是否采用边界保护、转换数据格式或重建流程，应由业务要求决定，不能规定所有越界都采用 clamp、所有空值都采用可选链。

### 3.5 设计示例：字符数量与字节容量

以已静态阅读的 HouseholdService 022 为设计例：栈指向 Uint16Array(buffer, 0, payload.length)；上游 ArrayBuffer 只分配了 payload.length 个字节。对于长度为 N 且 N > 0 的情况，N 个 16 位元素需要 2N 字节，容量与视图要求不一致。

因此，应记录“视图创建行”为异常位置，“分配容量及视图构造之间的不一致”为根因假设。候选可以调整容量，也可以改用按元素数分配的视图构造方式；最终选择取决于 buffer 的其他消费者和校验行为。应验证创建与校验的结果一致、正常数据可处理、边界数据行为正确。

此例说明无需设备就能细化机制和验证义务，但不代表已经生成并验证了有效应用补丁。本设计文档包含案例分析，不属于未来盲测求解器输入。

## 4. 模块之间传递什么

任务相关对象须能追溯 schema_version、task_id、source_snapshot_sha256 和适用的 run_id；条件结果通过嵌套请求范围绑定这些身份。位置保存原源码坐标，候选修改后的坐标单独表示。

| 对象 | 必要内容 | 不允许混淆 |
|---|---|---|
| Task | 允许输入、源码/日志哈希、可用能力、预算、评测协议标识 | 源码路径对应不等于运行版本一致 |
| Evidence | 来源类型、来源哈希、行范围/运行标识、观察内容、观察或推断 | 源码引用不能伪装成执行结果 |
| Diagnosis | 异常位置、候选根因位置、约束、生产者/消费者关系、证据和未知项 | 根因与修复落点分开 |
| ConditionRecord | 有限谓词结果、输入/诊断摘要、源码版本及对象/路径/采样点；决策另声明期望范围 | 固定合成输入与真实采样分开，计算状态不自动确认根因或修复成功 |
| CandidatePatch | 尝试序号、父快照、diff 哈希、修改意图、影响范围、行为义务 | 未生成候选和生成后失败均要留痕 |
| VerificationPlan | 要验证的假设、运行层次、输入类别、预期行为来源、所需能力 | 模型临时自测和独立验收测试分开 |
| VerificationResult | 每层状态、观察、错误类型、产物哈希、耗时与执行版本 | not_run、blocked、inconclusive 都不能记为 pass |
| Attempt | 采用的诊断、候选、检查、实际成本、下一步动作及理由 | 回退保留此前成本与尝试 |
| FinalReport | 初始/最终定位、最终补丁、终止状态、覆盖与未知、全成本 | 离线分析完成不等于任务修复完成 |

验证结果统一使用 pass / fail / not_run / blocked / inconclusive。任务终止状态使用 verified_under_protocol / unresolved / blocked / budget_exhausted；verified_under_protocol 只表示通过指定协议覆盖的检查，不表示未来永不出错。该状态还要求原始版本在相同目标协议下确实触发故障；原故障未复现时，不能仅凭补丁版本不崩溃宣称修复成功。

P0 的 `ActionProposal` 与主机授权函数已接入固定响应 Agent 的同步工具调用，动作结果账本支持完成回放和未知结果停止。`AcceptanceProtocol`、候选运行版本绑定、执行结果接纳和接受门仍只在合成记录上测试；独立准备者、可信打包器及真实执行适配器尚不存在。当前模拟 HTTP `ExecutionRequest` 只有执行层次，没有 check_id/场景 ID；正式应用适配必须升级此请求身份，让每个结果归属预冻结的具体检查，不能从日志内容或层次猜测。

## 5. 核心机制二：只为会改变修复决策的问题补证据

### 5.1 Agent 自主选择什么，Harness 固定什么

模型根据当前观察提出下一动作及依据，可选读代码、补查符号、更新假设、生成补丁、提出局部检查或请求运行。主控制器检查动作参数、版本、预算和可用能力，并执行工具；它不通过硬编码案例答案决定根因。最终是否接受补丁由固定验收协议决定。

Agent 的工作记录包括当前假设、支持/反驳事实、修复义务、候选版本和失败历史。下一轮保留必要记录并可回读原始产物，避免反复注入全仓源码和完整重复日志。已有反例只对相应输入、源码版本和条件有效，不推广成永久禁止某种修法。

### 5.2 明确的动作选择规则

| 当前信息 | 动作 | 目的 |
|---|---|---|
| 一个有依据的解释，修复方向清楚 | 直接生成候选，再做共同验收 | 简单案例不额外进行多假设辩论 |
| 多个解释，但对应同一修改与验收 | 合并等价修复方向，继续生成 | 不为不影响行动的争论付费 |
| 不同解释要求不同修法，缺少关键事实 | 提出能区分它们的检查，优先补查已有源码/日志 | 先决定该改哪里、保留什么 |
| 静态证据不够，存在有区分力的执行检查 | 在预算和能力允许时执行一次诊断探针 | 用观测改变选择；不是每例固定插桩 |
| 检查不能区分、缺环境或成本无法容纳 | 保留未知；若仍可提出候选则按未知状态尝试，否则结束 | 不把缺观测当作反驳，不无限等待 |
| 补丁后出现业务反例 | 关联到被违反的义务；修订补丁，必要时换假设 | 让失败具体影响下一步 |
| 同版本下重复相同补丁和稳定失败 | 要求有新证据的新动作，或停止 | 避免空转 |

探针提案必须列出待区分的假设/修法、所需输入、可能观测及观测后的动作。如果无论观察到什么都执行同一动作，就没有充分理由追加该探针。该规则是决策相关性启发式，不声称计算了真实信息增益或贝叶斯后验。

先过滤不可执行、没有区分力、依赖不成立的检查，再比较剩余检查的成本。成本优先取已有测量；无测量时显式使用源码读取、局部逻辑、完整构建/设备执行等粗粒度估计，不给出虚假的精确时间。模型的预测仅是待验证预期，实际结果不符合任一预测时标记不确定并重新审查。

### 5.3 自修复与验证

每轮从记录的基准构建完整候选，登记 diff 后做局部检查，再进行可用的实际验收。补丁引入编译错误时优先修正代码；原故障还在时先核对源码/产物和目标操作；新行为错误时把反例关联到具体义务；环境错误单独处理。

不同候选中，可复用的是经版本/依赖核对仍有效的源码事实；旧候选的执行通过结果不能自动证明新候选通过。所有组都必须完成相同的最终构建、目标、功能和回归验收。自适应选择只调整额外诊断和候选筛选，不省掉成功判定所需的测试。

初版暂定最多 3 个完整候选、额外执行诊断探针最多 1 次，受统一 Token 与墙钟上限约束。读取和每次模型决策同样计费；额外探针配额不包含最终协议要求的普通验收，也不代表验收可以无限运行。总时间、调用和验证重试仍受预算约束。

调用前检查可用预算，预留必要验证开销；缺少可信运行成本估计时保守限制并保留可能无法完成的状态，不声称一定满足未知的设备耗时。失败生成、重试和回退全部累计。Token/费用缺失为 null，不用文本长度冒充实际 usage。

### 5.4 一次任务的端到端决策示例

以缓冲区构造失败为例，H1 认为容量单位错、需要保留 16 位元素；H2 认为视图类型错、应按字节处理。Agent 先查下游消费与校验逻辑。若源码已表明按 16 位单元处理，就直接按 H1 生成，无需执行额外探针。若仍有关键歧义且能抽离逻辑，则可用已核验语义下的输入检查候选解释。

局部检查通过后仍需应用协议验收。如果补丁不崩溃却改变校验值，则记录“保留校验行为”义务的反例，修订相应候选。校验函数若也可能错误，就不能只靠两个相互配合的错误函数证明正确，需要独立业务依据。这个例子是设计推演，不是已运行结果。

## 6. 本机应用执行与模型接入

核心逻辑仍依赖统一 ExecutionBackend 协议，但真实应用的首选实现是本机受管作业进程和 SQLite 作业账本，不再要求 HTTP 服务或远程主机。W06 的 HTTPX/FastAPI 单作业模拟切片保留为状态转换与故障注入测试；它不产生应用证据，真实本机适配器尚未实现。基础模型拟由同一受管 Agent 经云端 API 调用，每次请求都须经过模型调用账本；不把 API 响应当作应用验证。真实调用前须核对私仓代码和日志的外发许可及最小发送范围。

| 接口 | 作用 |
|---|---|
| describe() | 返回 SDK、设备/模拟器、构建与测试能力、允许的执行层次和并发限制 |
| submit(request) | 提交版本绑定的构建或测试任务，返回 job_id |
| poll(job_id) | 返回排队、运行、完成或失败状态以及结构化结果 |
| cancel(job_id) | 请求停止；取消请求发出不等于已停止 |
| fetch_artifact(reference) | 取得构建日志、设备日志或结果，核对哈希 |

ExecutionRequest 必须绑定 task_id、完整运行源码哈希、补丁哈希、环境标识、测试协议哈希、初始状态方案、执行层次、重复序号和超时。幂等标识只对这些字段完全相同的一次逻辑调用有效；重跑使用新重复序号，不能错误复用历史成功。

本机适配器在启动前先只读盘点操作系统、可用内存和磁盘、已装工具及版本、项目构建依赖、设备/模拟器连接和驱动能力。开发数据中先挑两个预登记代表案例，核对完整工程、分析源码与运行源码谱系，并准备候选无关的目标操作、业务行为和回归 oracle。缺 SDK、设备或可信 oracle 的案例仍可离线分析，但不进入可宣称应用修复的运行阶段。具体工具版本与容量由案例需求及盘点决定；不能因设计文档列出了名称就视为已安装。

本机作业先在 `.dfx-local` 内写入版本绑定的请求、协议哈希和幂等键，再由 `scripts/local.ps1` 的受管入口启动单个独立作业进程。每次只接受预定类型的构建、安装、目标回放或行为/回归检查，模型没有任意 shell 权限。SQLite 保存 job_id、进程身份、候选/原版运行源码、check_id、场景、初始状态、重复序号和终态；同一请求恢复先核对进程、设备状态与产物，不盲目再执行。取消必须确认构建子进程和设备动作停止；超时或进程失联保留 inconclusive，不把它判成补丁失败或成功。产物按 job_id 归属并核对哈希与大小。

Agent 的 Python 环境与目标项目所需的 Node/Java/SDK、可能的 Hypium Python 环境分开。SDK、签名和设备参数由受管本机执行配置提供，不进入模型上下文；以项目匹配版本的命令行构建和场景操作为准，不假定任一案例已经支持模拟器。HarmonyOS 测试入口的此前参考是 [HarmonyOS 测试入门](https://developer.huawei.com/consumer/cn/testing/get-started/)；实际命令、工具版本和环境兼容性须在本机盘点后逐项验证。

W06 已有的 HTTP 提交/查询/取消/产物哈希模拟测试仍用于检查通用状态语义，不再扩展为必需的远程部署路径。真实本机适配器须另测中断后作业恢复、设备占用、进程树停止、磁盘预检、日志上限、产物错配和原版/候选版本绑定；只有带本机实际执行证据的检查结果可进入共同接受门。应用修复评测按 [评测口径](../preparation/metrics-and-gates.md) 用同一设备/环境、协议及预算比较 B0/B1/P，不把模拟通过计入成绩。

## 7. Skills 的具体位置

上下文、经验和 Skills 共同服务于一件事：依据当前根因假设和修复义务，选择有用证据及可迁移步骤，避免因异常相似而照搬错误修法。Deep Agents 继续承担通用工具循环及扩展接口，我们实现领域 harness，不另写 Agent runtime，不依赖模型微调。

当前 `policies.py` 提供四类静态 RuleCard，由 `consult_rule` 工具读取；已有诊断、义务、候选和合成反例交接。`knowledge.py`、`knowledge_retrieval.py` 和 `applicability.py` 提供主机批准经验、冻结检索、当前依据绑定与独立三态接口；`knowledge_run.py` 和 `knowledge_handoff.py` 将普通检索接入 SDK，覆盖 run 内批准原件、授权查询/回读及会话、报告、聚合和私有导出。三态 SDK 工具已接入实际发送和统一账本。`static_skills.py` 从批准人工条目生成完整静态过程，复用 SDK 原生 SkillsMiddleware；目录及完整正文绑定同一冻结清单，薄层核验资源、权限和检查点元数据。开启注入目录，关闭保留相同正文和读取能力；static_skill_handoff.py 将相同 read_skill 接入动作预算和实际 solver 输入，报告分别认证完整读取与后续真正可见性，冻结恢复、对照和私有导出。固定/模拟脚本及受管 CLI 已消费完整外部知识批准和策略；跨任务反馈固定来源并接纳人工待审核提议。独立 Skill 版本、事前验证计划和完整同池合成回执的程序接口已实现；演进判定/别名属于下一批，尚未提交，自动模型学习仍未接入。主机压缩仍按历史前缀处理。受管验收结论只见 STATUS，详细记录与不变量在 [模块规格第 3.1 节](../design-contracts.md#31-工作上下文经验与-skill-的实施契约) 定义；独立加载、实际发送和跨任务学习分别验收，不代表已有收益。

### 7.1 以当前修复决定组织工作上下文

沿用已有假设—证据—义务—候选—反例关系，不建立第二套状态台账。每一步突出当前选择的假设、须恢复和保留的行为、可能改变修法的未知项、当前候选及有效失败反馈；需要时回读原始依据。

SDK 模型边界已接入按可见授权回执组织的发送视图：先保留与当前决定有关的状态和引用闭包，再容纳源码、日志及完整历史组。必要记录和未被包表达的领域工具结果作为引用数据附入原启动任务消息；原 Graph 不变。仍相关的反例不能仅因出现较早而被摘要遗漏，其他候选的观察不能成为当前候选事实；摘要和经验判断不能覆盖主机检查结果，也不能将模型推断升级为可信业务义务。

实际顺序是原历史、工作上下文组织、可选通用压缩、最终发送；每个 solver 位点冻结材料并绑定实际请求。历史回读使用当时材料和回执，后续合法检查不改写过去输入。整理耗时保留，摘要调用计入原总预算；必要内容超过限额时明确停止，不通过丢失失败或放宽限制继续。新增选择开关在评测清单 schema 2/3/4 显式登记，通用压缩和其余共同预算不变；可关闭不等于已有收益。

当前 format 2 将完整原字节放在 run 内内容寻址材料库，不可改写计划清单保留每项归属、摘要和大小；主机核验完整材料，模型投影仅去掉逐文件 sources 回执清单，其他领域原文全部保留。材料和审计产物沿用原单产物限额，模型投影继续受共同 WorkingContextPolicy 预算约束；两者明确分代冻结，历史 inline 计划只读保持原解释。规模路径在单操作内复用已核验输入、去重入库和材料批量读；共享祖先在起止重核，文件原字节与身份继续核验，读取量按观察大小加增长哨兵而不放宽限额。缺失/改写材料拒绝，崩溃遗留材料只读计数，整体受本机磁盘/导出预算控制。模型读取工具、费用与公平门保持。该拆分及耗时治理属于工程基础；方法贡献仍须检验修复义务组织和经验适用性是否改善决定。合成规模边界与未决应用能力见 STATUS；经验、静态 Skill 和候选演进按 W07 包内依赖实施，具体义务见规格第 3.1 节。

### 7.2 经验迁移先核对前提

目标是从允许学习的开发任务提炼候选经验：触发操作、根因关系、修法前提、保留行为、有效查证步骤、失败方向及实际验证范围。成功和失败均可保存，但环境错误、结果未知或模型推断不能变成某种修法必然错误。旧任务证据只支持旧任务；新任务迁移程序性知识，仍须重新绑定自身事实。

当前独立基础的工作过程是：主机审查完整可见指导及材料用途，`HostMaterialRegistry` 捕获其原字节；`ExperienceDraft` 只选择批准材料 ID，`KnowledgeStore` 将指导与有限合成历史保存成不可变条目，再把明确条目、来源权限、求解分区和检索配置冻结成 `KnowledgeSnapshot`。经验内容含适用前提、未知时的问题、操作与观察分支、保留行为、反例和退出条件。每个来源都须允许目标用途和分区；显式排除的历史谱系拒绝进入快照。读具体快照时复核所有条目及原字节，不依赖当前库或新来源；构造和回读不创建目录，发布须使用主机预建的受管目录，整个引用集合有容量门。

这一基础依赖主机对完整指导和来源的审查。哈希核验字节及内部一致性，不能自动发现自然语言中的隐藏答案，也不认证历史描述指向的真实报告；排除谱系仅覆盖已声明历史。当前历史只允许主机合成 fixture，应用资格恒为无，未知和失败保留；提取成本若声明，只是主机记录，尚非模型调用账本证据。低层快照读取不自动感知实际任务分区；ApplicabilityStore 由外部主机批准固定 task/run、分析版本、日志、scope 和所选快照，读写均对照批准值，不从模型或磁盘自报扩大范围。普通检索的 SDK 准入再固定会话中的批准身份并核验实际动作，正式分区与谱系选择仍由主机负责。自动提炼、真实历史报告认证、真实提炼调用成本与 Skill 发布分别待接入，不能用这套接口宣称系统已经学会迁移。

首次程序启动由主机传入 `knowledge=HostKnowledgeInput(retriever, approval)`，在初始模型调用前将获准快照的材料、条目、snapshot 和完整索引精确复制到 run 内，批准绑定和规范 profile 同时固定。外部库的未选条目和旧查询不复制；profile 保存相对原件清单与完整身份，不保留绝对外部路径。恢复只接收主机显式原 `knowledge_approval`，按冻结 session profile 回读 run 原件，外部库无需存在；报告、聚合和导出也可从同一原件纯读重建。构造与回读不补索引、不修缺失来源，未启用知识时不创建文件，已有知识残留也不能通过删除配置降级。

复制前按既有门限核定原件、profile 和批准绑定的完整输出容量，实读当前 owner 并保守合计知识容量，预检关闭/审计所需读取；来源在复制前后分别 finish，复制后独立核验本地精确清单和完整索引派生行。链接、完整父路径或原字节漂移、未合并 sidecar、超限及缺项都拒绝，部分失败保留可审读原件。来源关闭、owner、run 回读和查询审查各有阶段限额，不把这些独立门称为覆盖全流程的全局 I/O 账本；协议字段和容量唯一维护在模块规格及契约代码。

独立检索已采用 SQLite 和明确标签作为可重放的基线，不增加向量服务或训练检索器。主机为具体快照显式建立派生索引；查询核对冻结权限范围、完整原件和索引全部行，只使用指导文本的实际值。标签按规范化后的精确重合、文本按去重查询词的子串命中计数，按冻结权重相加，以分数降序及条目 ID 升序分页；零匹配、缺标签和平台未知的条目继续参与候选排序。返回完整获准投影，保留前提与查证步骤，不因历史成功加分或赋予当前适用性。SQLite 只提供派生排序数据，缺失/破损不会从最新库补齐；原字节捕获后在受限内存连接解析，固定结构及语句，来源、索引和查询记录共用闭包容量门，累积读取与 SQL 工作量另受限。

查询记录绑定原输入、快照、索引、检索策略、匹配依据、完整命中及分页；保存是显式动作，底层 query 和历史回读无写入。SDK 的 search_experience 保存任务绑定查询并返回 query_id 及实际命中页的完整指导，read_experience 只回读该页或其真实成员，不接受模型自选库路径/范围。两工具经原工具授权、已记账 solver 响应及总工具预算；查询发布还先预检累计查询/检索审查空间，避免写入以后才发现无法审读。回读重新执行同一查询并比较全文，使普通检索和增强机制有可核验的共同知识入口。该排序是工程基线，不视为创新或提速证据；记录中的来源/索引字节表示唯一引用容量，不能当实际 Token 或运行耗时。

普通经验运行的会话/报告/completion 使用 11/8/5，显式三态策略的启停两组使用 12/9/6，显式静态策略启停使用 13/10/7，未启用知识的运行继续为 10/7/4。静态读取完整结果不含启停标识，只改变目录注入；严格 serializer 的只读 Graph 缓存准入和最终输入认证独立于主机批准。报告从完整原件、实际请求、查询、动作及父模型响应重建工具使用；磁盘上的孤立产物保留为未使用，缺报告或缺账本仍审读原件，费用和无法认证的使用保持未知。恢复前只读核对这些关联及原配置，漂移拒绝后不启用可写账本。评测清单 schema 3 固定同一快照、权限、检索配置、索引及批准原件；4 继承共享配置，显式登记 applicability_enabled。清单 5 另固定共同静态资源，显式登记 static_skills_enabled，启停均提供相同 20 项工具和完整静态读取结果。各相应代的启停组共享相同工具定义和总预算，关闭组保留普通检索与全文读取；各 run 的批准绑定和任务身份不进入共同知识身份。私有导出保全原件、实际请求和领域记录，包内回读无需原知识库；具体字段与旧代拒绝规则见模块规格第 1.2.2、1.3 及 3.1.2 节。

三态交接的工作过程是：主机批准任务与知识 → 保存绑定查询 → 从实际已发送输入取得当前诊断、假设和候选 → 冻结实查依据 → 提交逐前提判断 → 核验引用和版本 → 保存可尝试、暂停照搬或查证建议。每个经验前提都必须覆盖，unknown 原样返回该前提的查证问题；supported/contradicted 须有当前已登记引用，但含义仍由模型解释，主机核验不能提升为语义真值。原版源码/日志保持原版范围，执行事实及推断中的执行依据须对应当前候选；新诊断可以承接实查失败的前一候选，历史观察仍不能冒充修订候选事实。prepare/review/read 工具向 SDK 提供完整指导、问题与验证义务，不硬拒候选或改变共同接受门；合成验收结果见 STATUS，实际效果仍未知。

当时的原材料与上下文不可改写保存；回读核验冻结版本，并重新检查原诊断的引用、位置和版本关系，不用后来完成的检查重建旧判断，新证据须新上下文。独立接口的焦点仍为显式主机输入，SDK 外层通过 SolverVisibilityStore 认证其实际请求来源：完整已发送工具组和完全保留的工作上下文面板可作为依据，摘要中的 ID、被省略的记录及同一响应兄弟工具后产生的结果不可升格为已见。缺少已见焦点时保持 unknown 与普通指导。捕获/审计有总体容量和累计读取门，发布前还预检下一次审计和双份报告片段，查询另受自身限额；既有当前上下文构建阶段的任务/源码扫描尚无累计 I/O 账本，仍靠外层受管进程限制，不据此宣称整条路径的耗时或读取成本已经达标。具体边界由规格和契约代码维护。模型判断与主机来源核验分别记录：

| 与经验前提的关系 | 提供的内容 | 边界 |
|---|---|---|
| 有适用依据 | 可尝试步骤、保留义务及验证要求 | 历史成功不证明当前补丁正确 |
| 已有矛盾 | 不适用理由及相关反例 | 不因异常相似继续照搬修法 |
| 关键前提未知 | 区分修法的问题、源码查阅或可用检查步骤 | 不用相似度代替适用证据 |

例如，动态模式报错可能来自字面搜索，也可能来自允许正则的功能；前者的转义经验不能成为后者的统一修法。语义未知时先查调用方和消费行为。该例用于设计推演，不是数据案例答案。

经验提供建议，不赋予新工具权限、不替换共同验收，也不凭模型推断硬拒绝候选。没有适用经验时保留通用修复路径。

跨任务反馈先通过独立 FeedbackStore 固定来源。主机批准一条已结束的开发运行，程序核验案例选择、全部候选/检查、模型与动作成本和知识祖先权限，复制可独立重聚合的原件；原任务或库移走后仍能核验。失败和未知与成功一起保留，历史定位及失败归因不升级为当前事实。完整源码与原消息属于私有审计材料，不因捕获就获得求解权限。

首版从这些反馈接纳人工明确提议的完整经验过程，保留原 capsule 身份及部署范围，状态固定为待审核。它把“这份反馈是否可核验”和“这条经验是否值得迁移”分开：前者由程序落实，后者需要候选验证。此接口尚不调用模型自动总结、不改旧知识条目、不激活 Skill；后续提炼调用与批准桥接须另闭合成本和来源。具体对象及拒绝条件在模块规格第 3.1.2 节，完成证据只记 STATUS。

### 7.3 从经验形成可验证的 Skill

一个 Skill 对应可迁移的诊断/修复过程，包含适用前提、必需输入、查证步骤、观察分支、可选修改、保留义务、反例和退出条件，不对应案例编号或固定补丁。首批仍围绕初始化顺序、索引/字节边界、递归终止和动态正则，条件依据在 [模块规格第 3 节](../design-contracts.md#3-四类可迁移规则卡) 维护；修改时核对规则提示，避免语义漂移。

当前第一批通过 `SkillValidationStore` 实现版本与验证来源，实际验收见 STATUS。主机明确批准完整 host_curated 种子过程，或对原父版本及 FeedbackStore 的候选/capsule 分别提供完整外部批准；新版本绑定父版本和候选原件，保留全部过程及声明的学习谱系，权限只能继承或收窄。候选与 capsule 的完整私有来源复制到版本库，原任务/反馈库移走后仍能递归核验。模型学习调用为 not_run，成本为 null；保存版本不代表模型已自主提炼、部署或验证过新修法。

随后在任何角色运行目录创建前冻结验证计划。计划明确代表/边界两类案例的 CaseSelection、旧/新角色、预定工作路径、同一模型/工具/预算/接受协议及各自目标过程，排除父链和全部来源知识历史声明的学习谱系，重复日志或同谱系不能充作独立验证。主机当时观察所有 work 不存在，并记录源根身份和 UTC 时间；这是串行主机前置协议，不是独立可信时钟证明，也尚未绑定受管启动器。回执还核验原 session 不早于计划，不能事后补计划为既有运行增信。

现有评测清单 5 保持原含义，不改成不同知识版本比较。第一批使用两个单运行清单，共用包含旧/新完整投影的同一批准知识与静态资源池；计划分别指定应读的目标过程。回执从实际停止 SDK 合成运行的任务、全部候选/检查、账本、完整资源、请求和报告独立重聚合，核目标投影与版本一致、完整 read_skill 成功且在后续 solver 输入真正可见。读到另一角色过程（含普通经验搜索或完整回读）、未读或没有后续可见性仍保留完整结果/成本，标为未遵循或未知，不筛掉这些运行。这只能验证同池定向过程读取及记录链路，不能证明不同知识快照的收益或自主学习能力。

每份回执把原件与完整聚合保存为独立私有闭包，原运行移走后可只读重新核验；不执行模型、检查或 Graph。验证来源固定 candidate_validation、allow_learning=false，不能改标开发反馈回流。一次 API 的复制/闭合与递归回读共享读取预算，正式发布前预留完整回读成本；内部聚合/知识审计 I/O 仍有各自边界，不宣称整条流程已统一计量。失败、缺报告和未知费用保持原样，应用资格恒为无。演进判定、缩界/退回和冻结别名是下一批待提交能力，不由这些回执自动授予。

一次成功只产生候选 Skill。候选须在独立的开发验证案例及适用边界反例上与旧版本比较，保留业务验收及全部成本；证据不足保持候选。晋升只表示在登记的验证范围内值得使用，不证明普遍有效或逐例不劣。

新失败先区分选错 Skill、步骤缺陷、模型未遵循、工具/环境失败和结果未知。有依据的迁移反例用于缩窄前提、补充区分分支或退回旧版本，不将每次失败都升级为全局规则修改。保留修改前后版本与证据；在跑任务使用冻结快照，不随库更新改变续跑身份。

任务内自修复更新当前假设和候选；跨任务学习更新经验与 Skill。前者是基础闭环必需能力，后者可关闭，不作为 B0 前置条件。开发阶段可从允许的反馈学习，正式确认冻结经验和 Skills，不吸收隐藏答案；持续学习若单独评估，先测试后更新，与冻结成绩分开。详细字段与晋升/退回义务由模块规格拥有，依赖见实施计划，实际进度只记 STATUS。

## 8. 竞争力设计与成立条件

### 8.1 要超过什么，收益从哪里来

目标是在相同模型、工具权限和总预算下，相比配置合理的通用代码 Agent，用更少的错误尝试得到保留业务功能的正确补丁。框架选型降低开发成本，不自动产生效果优势；增加 Skills 或结构化字段也不算竞争力证据。

根据已有静态核查，不少日志已经包含业务源码位置，因此单纯栈映射可能不是主要提升空间。可争取的增量是从报错操作追到错误状态来源、保留业务语义、减少无效查证，以及让失败反馈修正具体假设。数据依据见 [数据核查第 3、4 节](../preparation/data-b-assessment.md)；尚无模型对照能证明这些就是强基线的实际瓶颈。

产品工程与方法贡献分开评估：日志适配、可靠工作区、HarmonyOS 执行和业务验收是完整系统能力；方法比较让各组共用这些能力，再检查领域决策机制是否仍有增量。不能因基线缺少设备工具或测试入口而宣称方法更强。

### 8.2 四个具体工作点

下表是第 3、5 节算法的实现与收益对应关系，不另设一套流程或参数。

| 工作点 | 具体执行与产物 | 预期收益及适用情况 | 主要失效方式 |
|---|---|---|---|
| 从异常追踪错误状态来源 | 从异常参数读取赋值、初始化、调用者及消费者；记录来源链，分开输出异常、根因和修复位置 | 对报错位置与状态生产位置不同的故障，提高根因命中和首次修复质量 | 错误关联、缺失跨模块信息；简单问题上增加阅读成本 |
| 让行为义务贯穿修复 | 每个候选说明恢复条件、保留行为及依据；生成补丁和分析反馈都引用同一义务 | 对多种补丁都能消除异常的故障，减少取消功能、截断数据等错误修复 | 模型臆测业务要求，排除正确补丁 |
| 按决策需要追加检查 | 明确不同观察分别导向什么修法；先查已有代码，必要时提出局部执行检查；已明确则直接修 | 对修法有歧义的任务减少试错；简单任务避免固定额外检查 | 检查无区分力、预测不成立或成本超过节省 |
| 用具体反例修订判断 | 绑定候选版本、输入、实际结果和被违反的义务；区分编译、原故障、业务回归与环境失败 | 避免同一错误反复出现，减少无效重试 | 误分类失败，或把旧版本反例不当地推广到新版本 |

前两项与反例关联共同支撑“修复义务贯穿全过程”；检查选择是可独立关闭的第二项增强。不是四个同时展开的独立研究课题。指标、比较组和接受规则统一在 [评测口径](../preparation/metrics-and-gates.md) 定义。

### 8.3 一例任务如何体现增量

沿用第 3.5 节的缓冲区设计例，下面是预期工作过程，不是一次实际成功轨迹，也不预设通用 Agent 必然失败。

| 步骤 | Agent 需要形成的决定 | 程序负责的边界 |
|---|---|---|
| 读取日志与源码 | 异常发生于视图创建，容量来源在上游分配；不是直接把栈顶当根因 | 校验位置和源码版本，保留原始依据 |
| 建立修复义务 | 恢复容量/元素宽度关系，同时保持数据编码和校验行为 | 区分运行规则、源码推断、独立业务要求；未知不伪装成事实 |
| 比较修法 | 扩大容量或改用字节视图，哪种符合消费方语义 | 不硬编码案例答案；模型推测不作为硬拒绝依据 |
| 选择是否查证 | 若下游语义明确则直接修；若有关键歧义，提出可区分两种修法的检查 | 约束能力与预算；预期结果不能记作执行结果 |
| 生成并验证 | 提交实际 diff；检查容量及业务行为，再进入应用共同验收 | 执行前登记候选；最终判据独立于模型自建检查 |
| 分析失败 | 若不崩溃但校验错误，回到编码/消费者假设，修订对应补丁 | 绑定具体反例，不将“无异常”当成功，也不清除失败成本 |

SDK 负责模型/工具循环；policies.py 提供四类可迁移规则卡及可关闭的义务/检查建议。diagnostics.py 接纳模型因果提案，decisions.py 将提议方向与已登记假设、证据、义务和有效合成失败绑定；建议可回读，候选可注明所选方向。基础与增强配置保留同一通用读码、编辑和检查工具；主机只给计划工具实际已有的源码/日志读取能力，当前没有诊断执行探针。workspace.py 负责候选冻结；verification.py 和 backends.py 当前仅绑定合成检查与模拟 HTTP 作业，应用执行证据仍待接入。规则卡不包含案例编号到补丁的映射。合成自检只证明记录交接和预设分支行为，不证明模型会提出正确的方向或提高修复率。

### 8.4 如何控制增强反而变差的风险

保留直接修复路径：原因与修复方向有依据时，不强制多假设讨论；未知类别走通用分析。路径选择只能依赖当时可见证据，不能读取隐藏标签或根据最终成绩选路径。判断规则在开发阶段调整，在确认评测前冻结。

模型推断的义务允许被后续证据推翻。只有来源明确且适用条件成立的规则、任务协议和实际检查结果，才可能形成程序约束；“模型说应如此”不足以拒绝候选。编译器成功、局部逻辑通过、设备无崩溃和业务正确是不同证据层次。

实现顺序是先建立完整强基线，再加入义务及反例关联，最后加入决策相关检查。先用合成路径验证规则确实被执行，真实资源到位后才判断效果；合成轨迹正确不证明模型会作出正确判断。新增失败和额外开销必须和新增成功一起审查。

若增强损害简单案例，先检查额外约束和调用是否必要；可关闭增强或调整基于证据的触发规则，但没有逐例不劣保证。不能为失败任务偷偷补跑一条满预算基线再合并成绩。无收益的增强不因已投入开发而进入比赛默认配置。

### 8.5 论文主张与路线收敛

拟议主线仍是修复义务贯穿诊断、补丁和检查选择。上下文、经验和 Skills 是这条主线的组织与迁移机制，不分别展开三个课题。待检验问题是：相同模型、知识、工具和总预算下，根据当前义务选择证据、核对经验前提，能否比普通摘要加相关案例检索减少错误迁移，最终得到更多保留功能的正确补丁？

组成部分已有近邻：ACE 使用轨迹反思与增量经验维护；SkillRevise 已包含保留约束、带迁移条件的原则记忆、证据绑定及候选重执行选择，也评估软件任务；TraceRepair 使用运行证据及修复探针。因此软件领域、三态适用性、记忆或 Skill 验证本身不证明新颖。我们在成熟方法上升级，来源及实际查阅范围见 [研究证据](../preparation/prior-art.md)，不宣称近邻完全没有这些机制。

拟议增量聚焦每一步修复决定的控制：当前操作和业务义务的证据状态决定返回可尝试修法还是区分问题，可信反例修订经验的迁移边界并回到后续选择。与 SkillRevise 的冷启动 Skill 修订相比，控制目标偏向求解中的经验使用与行为保持；这个区别仍须同知识对照、合理适配近邻和消融证明，不能靠命名或字段增加成立。

确认重点是有判别力的案例：相似异常因业务行为、对象状态或平台语义不同而需要不同修法。系统应能在适用时复用步骤，在未知时选择查证，在冲突时停止照搬。构造边界案例可以检验机制，但不代替独立真实缺陷上的主效果。反例和上下文更丰富也可能增加误判或成本，组合是否有收益须由同知识对照和消融确认。

证据链须连接实际决定与最终结果：关键义务或反例被保留，经验交接或检查选择实际改变判断，错误方向或无效查证减少，独立验收下正确修复增加或同等质量下成本降低。引用更多、轨迹更整齐、Skill 数量和模型自评有帮助都不足以支持主张；比较及指标只在评测口径维护。

比赛先保住可用强基线，无收益的增强关闭；开发成本不足时先收缩候选演进，不牺牲端到端验证。若质量持平而开销下降可评估效率贡献，若主机制无效则明确论文增量未成立。合成轨迹只证明软件行为，真实经验和晋升收益依赖应用证据。后续 CCF-B 层次的软件工程/应用 AI 工作须补独立确认、合理近邻比较和归因；数据不足时补公开或获授权任务，不复制日志扩大样本。具体会场未选定，不承诺录用；模型微调不列入当前路线。

## 9. 本机环境、资源限制与集中清理

### 9.1 使用方式与承诺边界

本机承担 Agent 控制、代码工作副本、HarmonyOS 构建、设备/模拟器回放和效果评测，不使用远程应用执行主机。基础模型拟由本机受管程序调用云端大模型 API；当前不安装模型权重、不安排小模型微调，也不启动真实调用。模型账号、具体型号、请求参数、外发数据边界和费用预算待确定。本机 SDK/模拟器是后续执行条件，不代表现在可以安装：先盘点容量、依赖和设备，再实现受管安装、运行、停止、证据保留和清理。现有轻量配置不能直接作为大型 SDK 或模拟器任务的已验收限额。

采用一个项目专属运行目录和一个 PowerShell 管理入口。用户能查看占用、停止本项目进程、清理缓存或完全移除运行环境；源码、Git、原始数据和已导出证据不会被普通清理删除。W01 实现目录归属与按计划清理，W02 实现 Job 进程保护与 Stop，W03 将同一保护用于 Init、pytest、文档/Ruff/Pyright 检查，W05 接入固定响应离线 Agent 的 repair/resume。W09/W10 沿用该保护完成只读聚合和本机私有证据导出；离线导出的实际验收进度只在 STATUS 记录。真实模型与应用任务仍未接入受管 Run。

“集中目录”不等于进程隔离，Python 虚拟环境不限制 CPU/内存。操作系统限制只覆盖管理入口创建的工作进程树，不覆盖 Codex、编辑器、用户其他程序，以及未纳入 Job 的既有设备服务；我们不能保证整台电脑绝不满载。Job Object 不提供 GPU 显存硬配额；若模拟器需要 GPU，必须另有监测与可确认停止机制才运行。磁盘采用容量预检与监测，不是内核硬配额；任意恶意代码不在本机执行，Job Object 也不是安全沙箱。

### 9.2 文件归属与安装边界

受跟踪的 [本机策略配置](../../configs/local-runtime.json) 是资源数值与开关的唯一来源。`execution.application_target=local` 是后续位置决定；`allow_local_harmony_sdk=false`、`allow_model_experiments=false` 和 `allow_application_experiments=false` 仍是当前禁用状态，不能解释成“应用会在远程跑”。`enforcement_status=offline_agent_guarded` 表示固定合成 Run、Init、pytest、质量检查、固定响应离线 Agent、只读聚合和 Export 使用相同 Job 保护；真实模型与应用执行仍未接入。运行时生效限制写入本地活动记录，不另维护一份项目进度台账。

| 位置 | 内容 | 清理性质 |
|---|---|---|
| .dfx-local/tools/、python/、env/ | 固定版本便携 uv、项目 Python、项目虚拟环境 | 可按依赖锁重新建立；清理不卸载系统 Python |
| .dfx-local/cache/、tmp/ | uv/pip/检查工具缓存，下载/解压临时目录，以及任务快照和未发布导出暂存 | 普通缓存空闲后可清理；检测到任务快照或导出暂存时须明确丢弃授权，不能一概按缓存删除 |
| .dfx-local/work/ | 每个 run 的可写源码副本、候选 diff、SQLite 检查点、检查意图与报告 | 终态只证明运行结束；非空 work 清理仍须明确丢弃授权，不共享可写硬链接到 data_B |
| 待盘点的本机 SDK/构建/设备缓存 | 后续项目专属路径及实际占用待定；如需外部安装位置，先建立明确 owner、限额和清理边界 | 当前不归 `.dfx-local` 清理器管理，不把系统既有 SDK 当成本项目文件删除 |
| .dfx-local/artifacts/、state/ | 受限进程日志、资源记录、管理状态 | 为证据/恢复数据，不按缓存自动删 |
| .dfx-local/owner.json | schema、仓库绝对路径、随机项目实例 ID、创建时间 | 管理入口生成，用于校验归属；不是删除授权本身 |
| runs/exports/ | 显式矩阵的本机私有证据包及清理回执 | 普通清理保留、独立显示大小；单包上限及与 managed 共用的磁盘预算约束累计占用，不视为已脱敏公开材料 |
| data_B/、archive/、既有 runs/ | 用户数据、历史归档与旧原型产物 | 报告现有占用但不接管、不移动、不默认清理 |

默认管理目录固定在仓库内；首次实现不支持随意更改为任意盘符根目录。若 SDK/构建缓存实测超出受管目录和磁盘预算，须先设计并验收项目专属的新位置与清理边界，再修改配置；不能直接改全局安装器或借用其他盘根目录。虚拟环境不承诺复制后可用。项目总占用报告分开列管理目录、未来项目专属 SDK/缓存、保留数据和导出包，不能只报 .dfx-local 造成“已全部清理”的误解。

入口脚本 scripts/local.ps1 提供 Prepare/Status/Clean/Stop/Init、固定合成/仓库测试/质量检查/离线 Agent/只读聚合的 Run，以及本机私有 Export/Verify；scripts/local_job.cs 创建和核验 Windows Job，scripts/local_export.ps1 在 Job 内调用固定导出接口。Prepare 不下载依赖；Init 只在 Job 内通过固定来源和 SHA-256 安装便携 uv/CPython 并同步锁定环境。Run 接受固定任务、仓库测试路径或已审查快照与固定脚本，不接受任意 shell。互操作代码使用系统 PowerShell/.NET 在当前进程编译，随后把 TEMP/TMP 指向受管 tmp；不安装全局 Python 包、系统工具或后台服务。导出内部使用 Windows 长路径接口，不改注册表或用户 PATH。真实模型与应用任务仍待接入，各入口验收证据见 STATUS。

安装时通过显式子进程环境设置 UV_CACHE_DIR、UV_PROJECT_ENVIRONMENT、UV_PYTHON_INSTALL_DIR、UV_PYTHON_BIN_DIR、UV_TOOL_DIR/UV_TOOL_BIN_DIR、TEMP/TMP 与 PYTHONPYCACHEPREFIX；Pyright 后备 Node 目录和 Ruff 缓存也路由到项目根。pytest 使用受管 basetemp，关闭持久 pytest 缓存和字节码写入，并在退出时删除自己的临时目录，避免不同 Windows 账户交替运行时产生不可访问目录。变量只在该子进程树生效，不改用户级 PATH、注册表、Shell profile、Conda base 或全局 pip。uv 固定版本/下载哈希，关闭 Python 注册表安装；环境同步使用 `uv sync --locked` 和项目 Python。正式 Agent 任务也须遵循同样入口，不用普通 `uv run` 绕过限制。

既有 Python/Git/ripgrep 可只读调用，但不由清理器接管；不存在时把新增工具放项目目录。若依赖需要不能受控的安装器、全局写入或后台服务，则报告不兼容，不自动提权全局安装。正式适配的凭据须通过进程环境传入，不写入 manifest、日志或导出包；当前固定/mock 模型入口不接受真实凭据。原始源码、日志和消息本身可能含私密内容，Export 的名称守卫不能证明其中没有秘密，不能直接作为公开包。第三方包可能绕过约定路径，安装验收要观察已知用户缓存位置的新增写入；“未观察到”不是系统级零写入证明。

### 9.3 资源限制怎样生效

配置中的数值是轻量工作负载的保守工程起点，尚未通过 HarmonyOS 构建或模拟器校准，也不是云端 API 的 Token/费用预算。具体数值只维护在配置文件；W08 前先以只读盘点和小型受管验证判断是否足够，放宽限制须有测量依据并形成显式配置变更，不允许接手模型遇到错误就自动增大。

| 资源 | 执行机制 | 越界或能力缺失时 |
|---|---|---|
| CPU、进程数 | Windows Job Object 对受管工作进程树设置 CPU hard cap 和活动进程数上限 | 无法建立/核验限制则拒绝工作进程继续运行，不能悄悄变为无限制 |
| 内存 | Job 的 committed memory 上限取配置绝对上限与物理内存比例的较小值；启动预留系统可用内存，运行时监测 | 分配可能失败；记录资源原因并停止任务。它不是对全机 RSS 或系统文件缓存的硬限制 |
| 并发 | 一个管理根的互斥锁与运行租约；合成、安装、测试、质量、离线 Agent、聚合和 Export 串行 | 第二个启动返回 busy；Stop/Status 不受工作锁阻挡 |
| 磁盘 | 所有受管任务预检和监测 managed 与 exports 合计逻辑大小及卷剩余空间；下载前估算，uv ZIP 流式限定字节；Export 另估算完整包和暂存新增 | 超过共同预算、导出单包上限或预留线则拒绝；不能通过不断换 Export ID 绕过累计限制，未来应用副本仍须单独估算 |
| 日志 | 受管任务的 stdout/stderr 经管道按字节上限保存，超额立即终止 Job 并继续排空 | 不在内存或磁盘无限堆积输出；留存日志标记截断 |
| 时间 | 单调时钟截止时间 + 子命令超时，采用资源配置与任务预算中的较严值 | 先请求退出，宽限结束后终止本任务 Job，记录 timeout/inconclusive |

生效计算：内存上限取 min(job_memory_cap_bytes, 总物理内存 × job_memory_fraction_of_physical)；磁盘预留取 max(min_free_disk_bytes, 卷总容量 × min_free_disk_fraction)。启动时要求可用物理内存足以容纳该内存预算和预留，运行时低于预留线则停止；CPU 配置百分比转换为 Windows CpuRate 时乘以 100。硬件容量通过 GlobalMemoryStatusEx 与 .NET DriveInfo 查询，避免依赖可能无权限的 WMI/CIM；读取失败保持未知并拒绝重任务。

受管任务启动顺序：读取并校验配置和 owner → 获取项目租约 → 检查空间/可用内存 → 创建并读回 Job 限制 → 以挂起状态创建工作进程 → 加入 Job → 恢复线程。子进程使用正常 CreateProcess 继承 Job，不允许 breakaway；不通过服务、计划任务或 WMI 绕过管理。启用 KILL_ON_JOB_CLOSE，Job 句柄不继承给工作进程；管理器异常退出后受管树退出已由合成测试验证。外层运行宿主若不支持 Job 嵌套，必须拒绝任务启动，不能无保护继续。

Stop 优先通过当前用户可访问的控制通道请求管理器停止，再使用经归属核对的 Job 终止受管进程。记录 PID、创建时间、可执行路径和实例 ID，不能按 python/node/java 进程名批量杀进程；PID 重用或失联时先核验，无法确认归属就报告，不扩大终止范围。默认前台运行，不遗留后台常驻进程；确需后台助手时隐藏窗口且纳入同一生命周期。

磁盘剩余空间须在监测周期中复查，也须在新写入/解压/下载前检查；ZIP 的声明大小不可信，按实际流出字节限制。Export 的单包上限只读取 configs/local-runtime.json 的 limits.max_export_package_bytes；managed 与 exports 共同使用既有 managed_disk_budget_bytes。复制前核对完整文件、清单和报告的预计新增字节；复制时检查卷剩余空间及已写/待写账面量，完工重扫实际占用，避免重复预留已复制部分。外部工具在两次观测间仍可能突增，或其他应用占满磁盘，因此不承诺目录级绝对硬上限。超限停止后保留一个预先准备、大小受限的结束记录；无足够空间时给出终端错误，不伪造保存成功。若本机不能提供所需的隔离或配额，真实应用任务保持 blocked，不以无保护的安装/运行替代。

### 9.4 统一命令与清理协议

下面列出统一接口。已有离线实现包括 Prepare/Status/Clean/Stop/Init、固定合成/测试/质量/离线 Agent/聚合 Run 及私有 Export/Verify；是否完成相应验收以 STATUS 为准。真实模型/应用 Run 尚未接入。

| 目标调用 | 行为 |
|---|---|
| .\scripts\local.ps1 Prepare | 建立或复核仓库内的 owner，不安装运行环境；同一 owner 重复调用幂等 |
| .\scripts\local.ps1 Status | 无模型、无安装地报告路径、各类字节、受管进程和限制是否生效；旧远程作业标记若存在仍报告未知项 |
| .\scripts\local.ps1 Init | 先检查容量和保护器，再建立固定版本 uv/Python/依赖环境；重复执行不重复安装 |
| .\scripts\local.ps1 Run -Scenario idle -Seconds 3 | 运行固定合成任务并记录限额、日志和结束原因 |
| .\scripts\local.ps1 Run -Task test -TestPath tests/test_sdk_compat.py | 在受管环境运行单个现存仓库测试文件；不接受任意命令或数据包脚本 |
| .\scripts\local.ps1 Run -Task docs/ruff/pyright | 在受管环境运行固定文档、Lint 或类型检查 |
| .\scripts\local.ps1 Run -Task offline -OfflineTaskPath TASK -OfflineScriptPath SCRIPT -OfflineWorkId ID | 在受管环境运行固定响应、合成判据的离线闭环；同一 ID 可加 -Resume 恢复，详情见原型说明 |
| .\scripts\local.ps1 Stop | 停止本项目受管工作树并核验退出；保留文件和证据，释放进程资源 |
| .\scripts\local.ps1 Export -EvaluationManifestPath MANIFEST -ExportId ID | 默认受管预览，披露私有内容范围与预计字节，保存固定计划并返回 PlanId；不创建最终包 |
| .\scripts\local.ps1 Export -EvaluationManifestPath MANIFEST -ExportId ID -Apply -PlanId HASH | 复核计划和源树，在私有暂存区复制、核验并发布新 runs/exports/ID；不覆盖目标或删除源 |
| .\scripts\local.ps1 Export -ExportId ID -Verify | 只从既有包核验完整清单与重聚合结果，不读取原输入，不执行模型或应用 |
| .\scripts\local.ps1 Clean -Scope cache/testcache/tmp/work/env/all | 默认只生成路径、估算字节、保留项、阻塞项和 plan_id，不删除 |
| .\scripts\local.ps1 Clean -Apply -PlanId ID | 执行仍有效、范围匹配的清理计划；资源/路径变化则要求重新生成计划 |

cache 清理缓存及 tmp；testcache 仅清理旧 pytest/pycache，tmp 仅处理临时目录；work 要先核对每个工作项为终态，非空时还须在预览和 Apply 请求中明确使用 -DiscardEvidence。cache/tmp/all 检测到任务快照或未发布导出暂存时同样要求明确丢弃；env 删除 tools/python/env，不触碰用户其他环境。all 移除整个 .dfx-local，artifacts/state 等证据仍阻止无丢弃授权的清理。一个矩阵包不覆盖其他运行、管理日志和全部 state，Export 不自动放行任何证据清理；先核验需保留的包，再由具体清理请求决定是否丢弃原记录。不得因目录被 Git 忽略而推定授权。Stop 不等于 Clean；停止不会删除证据，删缓存也不保证释放运行内存。

私有导出的输入是既有 EvaluationManifest。预览绑定 manifest 原字节、项目实例/owner、资源配置、完整矩阵及现有任务/work 树的路径、文件身份和哈希；缺失路径也固定，拒绝活动/历史未知作业、未终态、链接/共享文件、未知顶层及凭据类文件。计划只放固定 state/export-plan-ID.json，可以刷新合法的同 ID 旧计划，不能覆写未知文件、manifest 或输入树；Apply 重新派生全部范围和 PlanId，不能直接信任可编辑计划里的路径。

Apply 在受管 tmp 的独立 ex- 前缀目录构建暂存包，payload 保持原 task_path/work_path 相对布局。evaluation.json 保留输入原字节，aggregate-report.json 保存源端重算结果，package.json 绑定文件字节清单和计划；清单包含空目录及全部现有失败尝试，不为缺失 work 建空壳。批准知识运行保留 knowledge-profile.json、knowledge/、experience-bindings/ 和 experience-queries/，从包内任务和 run 原件重核固定知识、完整索引及查询关联，不依赖外部库。模型/动作账本、Graph SQLite 及知识索引均只读检查，非空 WAL/journal 拒绝而不自动恢复。包内再次聚合须与源端全文一致，源树/归属再核对且容量满足后才发布新的 runs/exports/ID；失败暂存仍未发布，不删除源证据。

Verify 的证据输入只取包内清单、哈希、源码/候选与账本以及重聚合结果，不反序列化或执行 Graph，不调用模型、工具或检查。新执行来源已嵌入 session/report，随原证据字节复制，无需升级 package schema；核验保存来源结构与摘要，不将它与当前 Git、运行源码或环境兼容身份强制匹配。执行入口仍核验当前环境 owner、依赖锁和自身租约；包的 owner_id 是导出来源实例，允许与当前实例不同。Clean all 保留的包可在重新 Prepare/Init 建立支持对应历史契约的受管环境后只读核验，无需恢复原任务或接管旧资源，不改写包、原输入和旧运行记录；仅保存当前受管日志/租约。来源 ID 与哈希均不是制作者认证或清理授权。包包含原始消息、任务源码和日志，标明未脱敏、仅本机私有、不可直接分享；内容一致不证明因果正确或可信业务验收。导出器的模块/schema 来源不补写旧 session 的 Git/lock/SDK 版本，嵌入的主机源码清单也不等于主机源码内容或环境备份。应用包、真实工具链版本和公开脱敏/正式提交仍按 W08 后的门槛实施。

清理必须在所有工作进程退出、设备动作结束、文件锁释放且历史未结作业已核对之后执行。先取得独占维护锁，阻止新任务进入；检查 owner、当前仓库、受管目录和目标真实绝对路径，拒绝路径链上的链接与目录外目标。目标内部可存在 uv/Python 安装生成的链接，但只接受解析后仍在管理根内的目标，清理时先删除链接本身，不跟随其遍历或删除目录外文件。计划绑定根 ID、范围、目标状态；执行前和递归遍历时再核验，遇到变化终止。不运行全局 pip/uv 缓存清理，也不使用 git clean -xfd。

清理器必须从仓库脚本/系统 PowerShell 运行，不能由将被删除的虚拟环境执行自身卸载。失败时返回已清、未清和原因，后续可重试；不得报告全部成功。all 完成时将受限清理回执写入 runs/exports，说明仍保留的数据和导出占用。原有 runs/archive 与共享缓存不在默认计划内，若用户另要求清理，单独列出确切目录和证据保留影响。

停止本机控制器不自动证明构建子进程和设备动作已结束；Stop 必须核对受管 Job、作业账本与设备状态，未能确认则保留 inconclusive 和相关产物，Clean 不清除恢复所需记录。旧版 `remote-jobs.json` 安全标记如存在仍阻止清理，待人工核对；新运行不创建远程作业。

### 9.5 必须先验证的保护与资料依据

本机保护通过隔离合成树核验路径、清理、进程派生、管理器崩溃、内存分配失败、持续输出、超时、并发互斥及进程身份。清理反例现由受管 pytest 执行既有 W01 脚本，并覆盖终态记录、任务快照和未发布导出保留。导出还核对实际工作进程祖先，兼容 Windows 虚拟环境启动器增加的进程层级，不能仅凭直接父进程判断。具体通过数量和最近环境观察统一见 STATUS，历史证据保留在 sessions。临时测试阈值只缩小不放大；未启动真实模型或应用任务。保护器测试不证明未来 HarmonyOS 安装器、设备服务、模拟器或 GPU 任务已受其覆盖；这些在 W08 前单独验收。

2026-09-21 核对了 [uv 环境变量](https://docs.astral.sh/uv/reference/environment/)、[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[CPU rate control](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information) 与 [扩展内存限制](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) 官方说明。2026-09-23 进一步核对了 [CreatePipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createpipe)、[ReadFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile) 和 [句柄继承](https://learn.microsoft.com/en-us/windows/win32/ipc/pipe-handle-inheritance) 的官方说明。资料说明所用机制；实际通过情况以本地合成测试记录为准。

## 10. 详细设计与接手边界

当前已确定方法主线、模块职责、本机资源/清理方案和分步验收任务。W01–W03 的本机管理和 SDK 接入、W04 的首批对象、W05 的固定响应离线闭环与模型账本接入、W06 的模拟 HTTP 作业协议、W07 的受控策略分支、P0 动作/接受契约、逐工具授权/恢复、因果记录与有限条件结果到修复决策交接已完成合成验证。W09/W10 的只读聚合和私有导出消费这些持久记录，其实际验收结果统一见 STATUS，不作为应用效果证据。可信采值与操作绑定的来源、接口和迁移设计见第 3.2.1 节及模块规格；独立合成绑定、凭据和不可改写登记已有实现，真实来源及新条件计算尚未接入。第 7 节的工作上下文和实际发送已有基础，主机批准知识及普通检索 SDK 切片已编码，验收只在 STATUS 记录；普通、三态和静态 Skill 的实际 SDK 与显式受管配置已有入口，跨任务反馈与学习按模块规格第 3.1 节继续分步实现。其余规则计算、正式模型适配、真实应用任务、独立业务反馈和设备恢复仍待编码和验证。资源数值对受管 Init/测试/质量/离线 Agent/聚合/Export 生效，不代表真实模型或设备任务已受管；具体进度见 STATUS。

接手者按 [实施计划](../project-work-plan.md) 的工作包顺序推进，先读当前包的输入、输出和反例用例；每次交付一个可检查的变更。实现中的局部选择可按契约自行决定；更换框架、放宽本机限制、改变评测判据或开启真实实验不属于随意实现细节，须按已授权边界处理并同步主文档。设计不能保证任何具体模型零错误，但可以使偏离易于发现、每步可回退。

原故障可复现、共同业务/回归协议通过、版本绑定一致，才可宣称按协议修复成功。无模型合成自检证明软件行为，不替代应用效果证据。
